Gameplay in Mowo is C++ written against an Unreal-style object layer: you subclass `AActor`, compose it from components, mark fields with reflection macros, and let a world tick it. Under that layer sits a flat entity-component system (ECS) that the renderer, physics and animation iterate for speed. [Visual Scripting](/docs/visual-scripting/) builds its node catalog from the same reflection data, so every system on these pages is usable from graphs too.

This section explains how the two layers fit together, then covers each gameplay system: physics, animation, audio, effects, AI, cameras, narrative, save games and the first-party gameplay plugins. The object model, reflection macros and modules are covered in depth in [Programming](/docs/programming/).

## Two layers, one scene

Every actor has a backing ECS entity. Gameplay code talks to the actor. Performance-critical systems read the entity. <Source symbol="AActor" />

<Flow steps={["Your AActor subclass", "Actor components (MActorComponent)", "Mirrored ECS components", "ECS systems (render, physics, animation)"]} highlight={0} caption="Gameplay code writes to actors and actor components. Components publish their state onto the actor's backing entity, which the flat systems iterate." />

The layers split the work like this:

| Layer | What it is | You use it for |
| --- | --- | --- |
| `MObject` | The garbage-collected base class with a reflected `MClass` | Anything with identity and lifetime |
| `AActor` / `MWorld` | Placeable objects and the world that ticks them | Gameplay objects, lifecycle, spawning |
| `MActorComponent` / `MSceneComponent` | Object-oriented behaviors attached to an actor | Meshes, lights, cameras, your own logic |
| ECS `World`, components, `System` | Plain-data components in archetype storage, processed by systems | High-volume data, engine subsystems |

An actor component such as `MStaticMeshComponent` also writes a plain `MeshRenderer` component onto the actor's entity, so the renderer's flat iteration sees it while your code keeps using the object interface. <Source symbol="MActorComponent" />

<Callout type="engine">
`AActor`, `MWorld` and the scene live in the **Game** module. Below it sit **SceneTypes** (render components), **AssetSystem**, the **ECS** module and **Components** (the base `TransformComponent` and `RelationshipComponent`). Larger systems such as AI, narrative, sequencer and PCG are feature modules the engine loads by name. See [Programming](/docs/programming/) for the module layout.
</Callout>

## Naming conventions

Mowo keeps Unreal's prefixes with one change: managed objects use `M` where Unreal uses `U`.

| Prefix | Meaning | Examples |
| --- | --- | --- |
| `M` | Garbage-collected object | `MObject`, `MWorld`, `MActorComponent` |
| `A` | Actor | `AActor`, `APawn`, `AGameMode` |
| `F` | Plain struct or value type | `FName`, `FTimerHandle` |
| `E` | Enum | `ETickGroup`, `ECollisionChannel` |
| `T` | Template | `TObjectPtr`, `TWeakObjectPtr` |
| `I` | Interface | `IDamageable` |

ECS components are plain structs named with a `Component` suffix, for example `TransformComponent` and `RigidBodyComponent`.

## Where your code lives

Your gameplay code lives in the project's game module, a shared library that depends on the engine and can be hot-reloaded while the editor runs; see [Programming](/docs/programming/) for game modules and plugins. `MowoSandbox` in the engine source is the reference template for a hot-reloadable module. The editor's class wizard, `mbt newclass` and the hot-reload loop are covered in [Working with C++](/docs/editor/working-with-cpp/).

A typical game-module class looks like this, taken from the sandbox template:

<Steps>
<Step title="Derive from an engine class">
Pick `AActor` for a placeable object, `MActorComponent` or `MSceneComponent` for a reusable behavior, or `APawn`/`ACharacter` for something a player or AI drives.
</Step>
<Step title="Annotate it for reflection">
Put `MCLASS()` before the class and `MGENERATED_BODY()` inside it. Mark fields with `MPROPERTY()` so they are saved with the scene and traced by the garbage collector. <Source symbol="ASandboxActor" />
</Step>
<Step title="Build components in the constructor">
Create components with `CreateDefaultSubobject<T>()` and pick a root with `SetRootComponent()`.
</Step>
<Step title="Override the lifecycle">
Override `BeginPlay`, `Tick` and `EndPlay`, and call the base implementation so components keep receiving their callbacks.
</Step>
</Steps>

<Callout type="note">
Every `MFUNCTION` you declare shows up in Visual Scripting automatically, because the node catalog is built by walking the class registry. You never register nodes by hand.
</Callout>

## What happens each frame

When the game is playing, the scene runs actor ticks in groups around the ECS update, and the physics step happens inside the ECS update. <Source symbol="AActor" />

<Flow steps={["PrePhysics actors", "DuringPhysics actors", "ECS systems (physics step, transforms)", "PostPhysics actors", "PostUpdateWork actors"]} highlight={2} caption="Actor tick groups run around the ECS system update. Put logic that must see settled physics poses in PostPhysics or later." />

With `p.OverlapDuringPhysics` on (the default), the physics steps run on a worker while the `DuringPhysics` group ticks. ECS systems have their own phase order (`PrePhysics`, `Physics`, `PostPhysics`, `PostUpdate`) inside that update. <Source symbol="System" />
