On Windows, a game reads its streamed files through Microsoft DirectStorage when the machine has it. DirectStorage batches many reads into the drive's queue, keeps NVMe drives busy, and can hand the bytes straight to the GPU. You change nothing in your project: a packaged game uses it automatically, and falls back to the ordinary file reads when it cannot.

## What it speeds up

Level loads and streaming read many files at once: scene preloads, texture and mesh streaming, asset loads started with `RequestAsyncLoad`, and anything else that goes through the engine's IO queue. With DirectStorage on, those reads of loose files and of uncompressed archive entries go to DirectStorage instead of the engine's own read threads. The bytes are identical; only how they reach memory changes.

## Which streamers use it

| Streamer | What it reads through the IO queue |
|---|---|
| Texture streaming | The mip range a texture needs, at the priority the caller asks for. A newer request for the same texture cancels the older read. |
| World partition cells | The cell's data file, parsed on a worker thread. A cell whose read fails is loaded the ordinary way. |
| Mesh streaming | A level that a view wants but that does not fit the frame's restore budget has its vertex and index spans read ahead, in one batch, and is restored from them a frame or two later. A mesh that goes away takes its pending reads with it. |
| Audio streaming | The next chunk of a streamed clip is read while the current one plays. A seek drops the pending read. |

Mesh and audio streaming keep the bytes they read in a small, capped memory budget until they are used, and give it back when the read is used, cancelled or fails. Every one of them falls back to the read it always did when a request is refused (the queue is not running, the budget is full, or `io.ReadAhead` is 0), is cancelled or fails, so the bytes a streamer ends up with are the same with or without DirectStorage. If DirectStorage (or any read backend) returns a span short, the engine reads it again the ordinary way.

Two things are not read through the queue: the shader archive, which is memory-mapped, and the pipeline-state record file, which is a few kilobytes. `io.ReadAhead` (default 1) turns the mesh and audio read-ahead off for A/B runs; the shutdown log prints how many read-aheads were used, read the old way, failed or cancelled.

What stays on the ordinary path, because the engine has to process the bytes before anything can use them:

- Archive entries that are block-compressed, encrypted or integrity-checked. They are read and decoded as before.
- Very large single reads (over 32 MiB), which the ordinary path already reads in bounded chunks.
- Files the platform cannot open for DirectStorage.

The gain depends on the drive. An NVMe drive with a deep queue gains the most, and a level load that is mostly many mid-size files gains more than one that is a few huge files. On a SATA SSD or a hard disk the drive is the limit and the difference is small. A machine that has just written or read the same files can serve them from the operating system's file cache, which hides the difference completely.

## What it measured

The engine's `streamer-read-ahead-bench` row replays the two patterns the stock streamers use against a cold file: an audio stream consuming consecutive 64 KB chunks with a quarter millisecond of decode work per chunk, and a mesh restore pass reading 8 levels (a 192 KB vertex span and a 48 KB index span each) from scattered offsets. Best of three rounds on one development machine, dev build, 48 MiB of audio and 192 mesh levels, Windows 11 with an NVMe drive (five runs, the range is shown):

| How the streamer reads | Audio stream | Mesh levels |
|---|---|---|
| Reads when it needs the bytes (before) | 330-353 ms | 213-232 ms |
| Read ahead, engine's async file reads | 218-234 ms | 103-109 ms |
| Read ahead, through DirectStorage | 248-291 ms | 106-114 ms |

Most of the gain is reading ahead: the audio stream overlaps the next chunk with the decode of the current one, and the mesh pass sends all its spans to the drive at once instead of one at a time. On this NVMe drive DirectStorage and the engine's own async reads came out about level for these small reads; DirectStorage's advantage shows with large sets and many requests in flight (see the load numbers in the engine's `directstorage-load-bench` row), and one drive is not a promise for yours. DirectStorage was slightly behind the async path on the audio pattern here: each 64 KB chunk is one request, and the engine's own async read has less per-request overhead. The bytes the streamers received were identical in all three modes.

## Turning it off

DirectStorage is on by default where it works. The console variable `io.DirectStorage` is read on every read, so it takes effect at once:

```ini
[ConsoleVariables]
io.DirectStorage=0
```

Set it to 0 to compare load times, or to rule it out while chasing a storage driver problem. See the [console variables reference](/docs/reference/console-variables/) for the current text.

## When it is not available

The game starts and loads normally, on the ordinary path, when:

- the game runs on macOS or Linux, where there is no DirectStorage;
- `dstorage.dll` or `dstoragecore.dll` is missing from the game's `Binaries` folder (the engine ships them with every Windows build);
- Windows cannot create a DirectStorage queue on the machine.

If DirectStorage fails a read it was handed, the engine reads that file again the ordinary way before reporting anything, so a driver problem costs time, not a failed load. The log line `[DirectStorage] read of ... failed` names the file and the error code, and the shutdown log prints how many reads fell back.

## Loading straight to the GPU

On the D3D12 backend the engine can also read a file range directly into a buffer or a texture, with the DirectStorage runtime decompressing GDeflate data on the GPU and zstd data on the CPU. The renderer reports a DirectStorage capability that is false on Vulkan, Metal and D3D11 and on a Windows machine without the DirectStorage DLLs; engine code checks it before using this path. This is an engine-level service; the stock texture and mesh streamers still read into memory first and upload from there.

## Per-vendor notes

These are the points Microsoft and the GPU vendors document for DirectStorage. They describe the platform, not a measurement of your game.

| Hardware | What to expect |
|---|---|
| NVIDIA | GDeflate runs on the GPU on every DirectX 12 card the driver supports. Keep the driver current: DirectStorage behaviour moves with it. |
| AMD | GDeflate runs on the GPU on current Radeon drivers. Older drivers can be slow or unstable with GPU decompression, and an update is the first fix. |
| Intel | Arc and recent integrated GPUs decompress on the GPU with current drivers. An older integrated GPU can end up with the decompression on the CPU, which competes with the game for cores. |
| Any GPU, old driver | The runtime falls back to decompressing on the CPU, so the load still works, slower. |

Storage matters as much as the GPU:

- **Windows version.** DirectStorage runs on Windows 10 (version 1909 and later) and Windows 11. Windows 11's storage stack lets a read skip more of the operating system on NVMe, so it gains more there.
- **Drive.** NVMe drives gain the most; SATA SSDs and hard disks gain little.
- **Filter drivers.** Antivirus, backup, software disk encryption and similar filters sit between the game and the drive. When one is present Windows can keep reads on the slower compatibility path, and the speed-up shrinks.
- **Compressed bytes on disk.** zstd and GDeflate shrink what the drive must deliver, so a compressed set loads faster on a slow drive; on a fast NVMe the decompression becomes the limit.
