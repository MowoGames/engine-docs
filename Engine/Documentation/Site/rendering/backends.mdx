Mowo has four rendering backends behind one RHI: <Fact id="rhiBackends" />. The renderer, Global Illumination, the editor and the tests run the same code on each. What changes between them is the feature ceiling, and which one starts by default on each platform.

## Defaults per platform

| Platform | Default | Other backends |
|---|---|---|
| Windows x64 | Direct3D 12 | Vulkan and Direct3D 11. All three are equal choices: a player picks one in the game's graphics settings, on the command line or in the Mowo Games Launcher, and it is also where a failed device creation falls back to. |
| macOS, Apple silicon | Metal | None. Metal is the only backend; there is no MoltenVK and the engine carries no Vulkan portability path. |
| Linux x64 | Vulkan | None. <Status /> |

The defaults are compiled into `SelectRendererAPI` (). Backends that do not belong to a platform compile as stubs that log a fatal error if called.

<Callout type="warning">
Linux is not available yet: there is no Linux installed build.
</Callout>

### Minimum API versions

| Backend | Requirement |
|---|---|
| Direct3D 12 | Feature level 12_0 |
| Direct3D 11 | Feature level 11_1, falling back to 11_0 |
| Vulkan | API 1.3 |
| Metal | Apple silicon; ray query needs a device that reports ray-tracing support |

## How the engine picks a backend

At startup the engine walks this list and stops at the first entry that names a backend:

<Flow steps={["-d3d12 / -dx12 / -d3d11 / -dx11 / -vulkan / -metal", "--rhi=<name>", "User config rendering.graphics_api", "Project Config/Engine.ini", "Config/Engine.ini next to the game or exe", "Platform default"]} caption="Backend selection order in SelectRendererAPI." />

1. **Shorthand switches.** `-d3d12`, `-dx12`, `-d3d11`, `-dx11`, `-vulkan` and `-metal` force a backend. A switch for a backend this build does not contain logs a warning and keeps the default.
2. **`--rhi=`** with `vulkan`, `d3d12`, `d3d11` or `metal`. An unknown name logs a warning and uses the platform default.
3. **The persisted setting `rendering.graphics_api`.** The engine reads the player's own user config first (the **Graphics API** row of the game's settings writes it), then the project's `Config/Engine.ini` (with `DefaultEngine.ini` under it), then a `Config` folder beside the packaged game root, the executable or the working directory.
4. **The platform default.**

A persisted backend that this platform cannot run (for example `vulkan` saved on Windows and opened on a Mac) logs a warning and falls back to the default instead of failing.

<Callout type="note">
A **release** build of the player keeps only the player-facing command-line switches. The six backend shorthands are on that list; `--rhi=` and `--cvar=` are dropped (). Tell players to use `-dx11` or `-vulkan`, not `--rhi=`.
</Callout>

## Automatic fallback

The chosen backend is only the first candidate. If it fails to initialize, `Renderer::Init` tries the rest of the platform's list in order ():

| Platform | Fallback order after the requested backend |
|---|---|
| Windows | D3D12, Vulkan, D3D11 (the requested one is never retried) |
| macOS | Metal (the only real backend there) |
| Linux | Vulkan |

A player can reorder the Windows chain: `rendering.graphics_api_order=vulkan,d3d11,d3d12` in the user config, or `-rhi-order=vulkan,d3d11,d3d12` for one run. The requested backend still goes first, then the listed ones in that order, then any left in the default order.

When a fallback wins, the log says `Requested backend X unavailable — running on Y instead`, and the player is told in a message box that names the API that failed, the reason and the one that runs instead. The same sentence heads the **Graphics API** row in the settings. If nothing starts, the engine stops with a fatal error.

## Let players choose the API

On Windows every game offers Direct3D 12, Vulkan and Direct3D 11 as equal choices. Nothing is hidden from the list except backends this build does not contain or this machine cannot run.

- **In the game.** The settings screen has a **Graphics API** row (Display) listing exactly those backends. The pick is written to the player's own user config as `rendering.graphics_api` and applies at the next launch: changing the API stays restart-only until the live switch is allowed for players. The row is absent on macOS and Linux, where there is nothing to choose.
- **On the command line.** `-d3d12`, `-vulkan` and `-d3d11` beat every saved setting for one run.
- **In the Mowo Games Launcher.** A game's **Manage** menu has a **Graphics API** entry that cycles the game default, Direct3D 12, Vulkan and Direct3D 11; the launcher then starts the game with the matching switch, unless the player's own launch options already name one.

What D3D11 or Vulkan lack is hidden by the capability gating, not by leaving them out: choosing Direct3D 11 removes the ray tracing, meshlet and bindless settings from the game's own screens.

## Choose a backend for your project

<Steps>
<Step title="Open the Rendering settings">
In Mowo Editor, open **Project Settings**, then the **Rendering** page, and find the **Graphics API** row ().
</Step>
<Step title="Pick the backend">
The dropdown lists only backends that exist on this machine. The caption under it names the backend and GPU that are running now.
</Step>
<Step title="Restart">
The change is written to your project's `Config/Engine.ini` as `rendering.graphics_api` and takes effect on the next launch of the editor or the game: the editor's own UI renderer, viewports and thumbnails hold device objects, so it relaunches on the new backend instead of switching under them (**Restart now** in the settings banner does it). The setting ships with a packaged build.

A live switch exists behind `r.LiveAPISwitch` (off by default). Every holder of GPU objects registers a release and a rebuild with `FGpuLifecycle`; the switch releases them, moves the device to the new backend, rebuilds them, and puts the old backend back if the new one does not come up or a holder cannot rebuild. Thumbnails and preview scenes already take part. The editor's UI widgets hold device textures with no rebuild path, so while they are registered as a blocker the switch reports itself unavailable and the Restart row stays.
</Step>
</Steps>

### From gameplay code or Visual Scripting

`MRenderingStatics` exposes the same selector to graphs (<Source symbol="MRenderingStatics" />). `GetGraphicsApi()` returns the live backend name. `RequestGraphicsApi("d3d12")` writes the project setting and flags a restart that `IsGraphicsApiRestartPending()` reports; it never switches the live device.

In C++ you can ask which backend is running and what its API allows:

```cpp title="BackendInfo.cpp" wrap
#include "RHI/RendererAPI.h"
#include "RHI/Renderer.h"

const Mowo::RendererAPIType api = Mowo::RendererAPI::GetCurrent();
const char* name = Mowo::RendererAPI::Name(api);

const bool apiCanRayTrace = Mowo::FRHIApiCeiling::SupportsRayTracing(api);
const bool apiHasRtPipelines = Mowo::FRHIApiCeiling::SupportsRayTracingPipeline(api);
const bool deviceCanRayTrace = Mowo::Renderer::GetCapabilities().SupportsRayQuery;

(void)name;
(void)apiCanRayTrace;
(void)apiHasRtPipelines;
(void)deviceCanRayTrace;
```

Ask `FRHIApiCeiling` whether a feature is possible on the API, and `RendererCapabilities` whether this device supports it now. The editor uses the same two axes: it hides a control the active API can never support and greys one that this GPU or build lacks.

## What each API can do

This is the API ceiling from `FRHIApiCeiling`. A specific GPU can support less.

| Feature | D3D12 | Vulkan | Metal | D3D11 |
|---|---|---|---|---|
| Ray query (inline ray tracing) | Yes | Yes | Yes | No |
| Ray-tracing pipelines and shader binding table | Yes | Yes | No | No |
| Mesh shaders (meshlet path) | Yes | Yes | Experimental, off by default (`r.Metal.MeshShaders`) | No |
| Bindless resources | Yes | Yes | API allows it; reported off today | No |
| 64-bit shader integers | Yes | Yes | API allows it; reported off today | No |
| Async compute queue | Yes | Yes | Yes | No |
| Vendor upscalers | DLSS, FSR, XeSS | DLSS, FSR, XeSS | MetalFX | DLSS, XeSS |
| Low latency | Reflex, Anti-Lag 2, XeLL | Reflex | None | Reflex |
| Frame generation <Status /> | FSR3, DLSS-G, XeSS-FG | FSR3, DLSS-G | MetalFX | No |

Notes on the table:

- Metal traces through `intersection_query`, so it has ray query but no ray-tracing pipeline objects. A feature that needs a shader binding table checks `SupportsRayTracingPipeline`, which is true only for Vulkan and D3D12.
- Metal reports bindless and 64-bit shader integers as unavailable (). These are engine gaps, not API limits.
- On D3D11, XeSS uses its native D3D11 path and DLSS and Reflex go through Streamline. FSR and every frame-generation backend need D3D12 or Vulkan ().
- XeSS frame generation only exists as a DXGI proxy swapchain, so it can never run on Vulkan.
- The D3D12 async-compute lane is on by default; `r.D3D12.AsyncCompute 0` records every async candidate on the direct queue instead.
- Frame generation is written for every listed backend but has not been verified on hardware. Treat it as in development.

### The capability matrix

Beyond the handful of predicates above, every device feature the RHI can gate on is one value of `ERHIFeature` (about 60: enhanced barriers, wave operations, 16-bit shader math, descriptor buffers, placed resources, residency sets, sparse resources, work graphs, cooperative vectors, opacity micromaps, tile-based and memoryless attachments, present wait, calibrated timestamps, DirectStorage and more). `FRHIFeatureMatrix` holds one row per feature with the lowest API version that can ever express it on each backend (Vulkan 1.3, Direct3D 12 feature level, Direct3D 11.x, Metal 3 or 4), and `FRHIApiCeiling::Supports(api, feature)` reads it. Each backend fills `RendererCapabilities` from device queries and reports the API version it negotiated in `ApiMajor` and `ApiMinor`; `FRHIFeatureMatrix::Validate` names every bit a backend raised that its API version cannot claim, and the `rhi-caps-consistency` test row runs it on the live device and prints the whole table.

A bit marked "probe only" in the header is set from a driver query but has no engine call behind it yet; the renderer never reads one.

The ceiling is applied once, when the device comes up: `FRHIFeatureMatrix::Sanitize` lowers any bit the API at its negotiated version cannot express, so nothing downstream can see a feature the backend lacks, and the log names the backend whose probe over-claimed. Gates read `FRHIFeatureMatrix::Effective` (ceiling and device together). The game settings screen builds its device profile the same way (`FAIGGDeviceProfile::FromCapabilities`), which is why a Direct3D 11 game offers no ray tracing, meshlet, frame generation, bindless, variable-rate shading or async-compute option whatever the driver reports. The `rhi-feature-gate-walk` tests lie to every API with every bit raised and check that nothing survives, and scan the renderer, settings and editor sources so a gate that reads a capability the matrix has no row for fails the build of the tests.

### Shader model, wave operations and 16-bit math

Shaders are written once in HLSL and compiled per API. Three device features change which variant a pass loads, and each is a permutation of the same source, so a device without the feature runs the same shader on its fallback variant:

| Feature | Variant | Bit | Off switch |
|---|---|---|---|
| Wave (subgroup) operations: one atomic per wave instead of one per lane | `WAVE_OPS` | `WaveOps` | `r.Shader.WaveOps 0` |
| Native 16-bit shader math | `FP16`, compiled with 16-bit types | `Float16` | `r.Shader.Float16 0` |
| Shader model 6.7 compute | `cs_6_7` blob | `ShaderModel` of 67 or more on Direct3D 12 | none; the shader is skipped on older devices |

`FShaderPlatform::WaveOpsPermutation` and `FShaderPlatform::Float16Permutation` return the permutation a pass asks for (empty when the device or the variable says no). Direct3D 11 compiles through FXC at shader model 5 and has neither, so it always runs the base variant. The foliage instance cull is the first engine pass on `WAVE_OPS`: it appends its survivors with one atomic per wave and gives the same instance list as the lane-atomic version.

### Vulkan 1.4

The instance asks for Vulkan 1.4 when the loader offers it and reports the negotiated version, so 1.4 core features (push descriptors, host image copy, dynamic-rendering local read) show up as capability bits without the extension spelling. Vulkan 1.3 stays the floor.

### Image barriers on Direct3D 12

On a device that reports enhanced barriers the renderer records image transitions as enhanced barriers: each names the pipeline stages it waits on and releases, the access it makes visible and the exact texture layout, instead of draining the pipe the way a legacy resource barrier does. Images placed over aliased memory, the async-compute lane and the copy queue keep legacy barriers. `r.D3D12.EnhancedBarriers 0` returns every image to legacy barriers.

CPU-written dynamic buffers (uniform, dynamic vertex and dynamic index) go to the GPU upload heap on a device with resizable BAR, so the GPU reads them from video memory; `r.D3D12.GpuUploadHeap 0` puts them back in system memory.

### Attachments that never leave the pass

A render pass can declare what happens to an attachment's contents: a `DontCare` store action (nothing reads it afterwards), a `DontCare` load (the pass writes every pixel), or a transient attachment (it lives and dies inside the pass and is never sampled or copied). `FRenderPassAttachmentPolicy` turns the declaration into what the device does, from the capability bits: Vulkan sets the attachment's load and store operations, D3D12 discards the resource at the start or end of the pass, Metal sets the load and store actions, and D3D11 ignores them. A transient attachment is backed by lazily allocated memory where Vulkan reports a memory type for it, by no memory at all on Metal (`StorageModeMemoryless`), and by an ordinary target everywhere else, so a desktop device draws the same image. `TransientAttachments`, `MemorylessAttachments` and `LoadStoreActions` are the bits; a framebuffer that wraps images it did not create stays ordinary, and `ValidateReadAfterPass` refuses a declaration whose attachment a later pass reads. The `rdg-transient-attachments` row creates such a framebuffer on the live device and checks it reports what the device promised.

### What D3D11 costs you

D3D11 has no meshlets, no ray tracing, no bindless resources, no async compute, no indirect-count draws and no frame generation. Features that need them fall back or switch off. Because players can pick D3D11 and also land on it when the others fail, test your game on it with `-dx11`.

## Fallbacks inside a backend

Features that the device lacks fall back each frame without configuration:

- The meshlet G-Buffer falls back to the classic vertex pipeline.
- A vendor upscaler that is missing falls back to TAA.
- Ray-traced reflections, AO and sun shadows fall back to screen-space reflections, GTAO and shadow maps.

## Backend console variables

A few variables tune one backend. They are listed with the rest at [Console variables](/docs/reference/console-variables/).

| Variable | Default | Effect |
|---|---|---|
| `r.D3D12.AsyncCompute` | 1 | The D3D12 async-compute lane. 0 records the work on the direct queue. |
| `r.D3D12.FrameLatencyWaitable` | 1 | Throttle D3D12 on a frame-latency waitable swapchain. |
| `r.D3D12.MaxFrameLatency` | 2 | Presents D3D12 may queue ahead of the display. 1 is lowest latency. |
| `r.D3D12.EnhancedBarriers` | 1 | Record image transitions with enhanced barriers where the device reports them. 0 uses legacy resource barriers. |
| `r.D3D12.GpuUploadHeap` | 1 | Place dynamic uniform, vertex and index buffers in the GPU upload heap (resizable BAR). 0 uses system memory. |
| `r.Shader.WaveOps` | 1 | Use the wave-operation shader variants on devices that report wave operations. Read when a pipeline is created. |
| `r.Shader.Float16` | 1 | Use the native 16-bit shader variants on devices that report them. Read when a pipeline is created. |
| `r.D3D11.RenderThread` | 1 | Run D3D11 with the render and RHI threads. Read at startup. |
| `r.LiveAPISwitch` | 0 | Let the Graphics API picker switch the backend without a restart when no holder blocks it. |
| `r.Vulkan.PipelineReuse` | 1 | Share one `VkPipeline` between identical pipeline specs. |
| `r.Metal.MeshShaders` | 0 | Report mesh-shader support on Metal. Experimental. |
| `r.Metal.MTL4` | 0 | Use the Metal 4 command model where the OS supports it. |
| `r.GpuMarkers` | 1 | Name every GPU scope for PIX, RenderDoc, Nsight or Xcode captures. |
