`Engine` (in the EngineLoop module, binary `MowoEngine`) owns the window, the frame loop, the engine subsystems and the scenes. An application never instantiates it directly; it subclasses it and overrides a few virtual functions. <Source path="Engine/Source/Runtime/EngineLoop/Private/Core/Engine.h" />

## The hosts

| Subclass | Executable | Role |
| --- | --- | --- |
| `MGameEngine` | MowoGame, or your project's game target | The game player, in the GameHost module |
| `MServerEngine` | MowoServer | The headless dedicated server |
| `MEditorEngine` | MowoEditor | The editor |

Each overrides three hooks; the base versions do nothing:

```cpp nocompile
class MGameEngine : public Engine {
	void Tick(float dt) override;
	void Draw() override;
	void RouteEvent(Event& e) override;
};
```

- `Tick(float dt)` runs the app's per-frame logic and records the scene's rendering.
- `Draw()` submits UI.
- `RouteEvent(Event&)` sees each queued event before the per-type handlers.

`Engine` derives from `MObject` and roots itself, so the garbage collector treats it as a root. The `GEngine` macro returns the process-wide instance; it is null before `Initialize` and after `Shutdown`, so guard code that can run outside a live session.

## Lifecycle

```cpp nocompile
engine.Initialize(config);
engine.Run();
engine.Shutdown();
```

`Initialize(const EngineConfig&)` brings up the window, the graphics device, the job system, the virtual filesystem and engine content, loads the [feature modules](/docs/programming/architecture/#feature-modules) and the engine plugins, and applies the command line and config to console variables. With a headless config (the dedicated server) it skips the window, the GPU and audio, but still starts the job system so the same loop runs. `Shutdown()` deinitializes engine subsystems in reverse order of creation.

## The frame

`Engine::Run` repeats a fixed sequence until the window closes. Simplified:

1. Advance the frame clock (`FTime::BeginFrame`) and the stats registry.
2. Wait for the render and RHI threads where the host does not render ahead; begin the profiler frame; flush deferred deletes.
3. Apply pending [live coding](/docs/programming/live-coding/) patches and hot reloads.
4. Step the garbage collector (incremental by default; see [Objects and garbage collection](/docs/programming/objects-and-gc/)).
5. Pump window messages and update input.
6. `Renderer::BeginFrame`, then the UI overlay's begin frame.
7. Poll the network, dispatch queued `EventBus` events, run main-thread jobs, tick timers.
8. **`Tick(dt)`**, then **`Draw()`**.
9. End the overlay frame, submit, present.
10. Reset the frame allocator and end the profiler frame; cap the frame rate when the window is unfocused.

<Flow steps={["BeginFrame", "Events and jobs", "Tick", "Draw", "Overlay end", "Present"]} highlight={2} caption="Tick and Draw record into the same frame. Nothing may render after the swapchain pass." />

<Callout type="warning">
Never record GPU work outside Tick and Draw. While the window is minimized the frame is not begun at all, so a host that records unconditionally crashes; the loop decides once per frame whether it renders and gates both `BeginFrame` and `Present` on that one decision.
</Callout>

### Delta time

`Tick` receives the clamped frame delta. `FTime` exposes the same clock to any module: real time, the clamped and unclamped deltas, game time scaled by time dilation and frozen while paused, and the frame number. See [Core libraries](/docs/programming/core-libraries/#time).

## Render and RHI threads

The game and editor hosts split the frame across threads by default. The game thread produces a self-contained frame packet; the render thread consumes it and records GPU work; the RHI thread submits and presents. With both threads running, the game thread produces frame N while the render thread records frame N−1.

Because of that overlap, game-thread code must never record into the current frame's command buffer: queue the work for the render thread instead.

| Switch | Effect |
| --- | --- |
| `--no-render-thread` or `-onethread` | Record on the game thread |
| `--no-rhi-thread` | Submit and present on the render thread |
| `--no-overlap` | Keep both threads but do not overlap produce and consume |

These switches are read by `MGameEngine` and `MEditorEngine`. <Source path="Engine/Source/Runtime/GameHost/Private/MGameEngine.cpp" />

## Writing your own host

A program built on the engine (a tool with a window) subclasses `Engine` the same way and links EngineLoop. The crash reporter (`MCrashReporterEngine`) and MowoInsights (`MInsightsEngine`) are small examples. <Source path="Engine/Source/Programs/MowoInsights/Private/MowoInsights.cpp" /> `mbt new-program` scaffolds a new program; see [Build tool](/docs/build-tool/).
