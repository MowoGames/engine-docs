A plugin is a folder with a `.mplugin` manifest and, usually, C++ modules and a `Content/` folder. When a project enables it, its content mounts into the virtual filesystem, its modules load and register their types, and its editor module (if it has one) extends the editor. The engine ships <Fact id="plugins.length" /> plugins in `Engine/Plugins/`, opt-in except Editor Utility Scripting, which is editor-only and on by default, and lists its feature modules beside them.

## Layout

```text
MyPlugin/
  MyPlugin.mplugin            JSON manifest
  MyPlugin.Build.cs           the runtime module's rules
  Public/MyPlugin/            reflected headers
  Private/                    sources
  Content/                    assets, mounted at Plugins/MyPlugin
  Config/                     INI layers merged into the project's config, optional
  Shaders/                    HLSL, optional
  Source/ThirdParty/<Lib>/    a vendored library the plugin carries, optional
```

A plugin lives either in `Engine/Plugins/<Name>/` (shared by every project on the machine, loaded at engine start-up, read-only in the editor) or in `<Project>/Plugins/<Name>/` (committed with the project, loaded when the project opens).

## The manifest

```json title="MyPlugin.mplugin"
{
  "fileVersion": 1,
  "name": "MyPlugin",
  "friendlyName": "My Plugin",
  "version": "1.0.0",
  "description": "What the plugin adds, in one or two sentences.",
  "author": "Studio",
  "category": "Gameplay",
  "icon": "swords",
  "enabledByDefault": false,
  "content": true,
  "engineVersion": "0.3",
  "dependencies": [],
  "modules": [
    { "name": "MyPlugin", "type": "Runtime", "loadingPhase": "Default" },
    { "name": "MyPluginEditor", "type": "Editor", "loadingPhase": "Default" }
  ]
}
```

| Key | Meaning |
| --- | --- |
| `fileVersion` | The manifest schema version, currently 1 |
| `name` | The plugin's identity; one plugin per name |
| `content` | `true` mounts the plugin's `Content/` folder |
| `enabledByDefault` | Used when the project's `Config/Plugins.ini` says nothing; `false` when the key is absent |
| `engineVersion` | The engine major.minor the plugin targets; another version blocks the plugin |
| `dependencies` | Plugins that must be enabled and loadable first: a name, or an object with `name`, `optional` and `version` |
| `modules` | The C++ modules to load: a name, or an object with `name`, `type`, `loadingPhase`, `platforms` and `targets` |
| `supportedPlatforms`, `supportedTargets` | Where the plugin may be live; see [Platforms and targets](#platforms-and-targets) |
| `nativeDependencies` | Gradle, manifest, CocoaPods and Swift package entries for Android and iOS; see [Native dependencies](#native-dependencies) |
| `capabilities` | What the plugin needs the project to allow: `network`, `filesystem`, `process`, `native-code`, `editor-scripting`; see [Trusting third-party plugins](#trusting-third-party-plugins) |
| `category` | One of the fixed categories below |
| `requiresOnline`, `server`, `dlc`, `beta`, `marketplaceUrl`, `docsUrl`, `supportUrl` | Flags and links the Plugins window and packaging read |

The manifest is read against a schema, by the engine and by `mbt` alike. A key the schema does not know is a warning in the log; a value of the wrong type, or an unknown module `type` or `loadingPhase`, makes the plugin unreadable and it is skipped with the message. The categories are Gameplay, Animation, Audio, Rendering, World Building, Foliage, Networking, Online, Physics, UI, 2D, Content, Editor, Scripting, Developer Tools and Other.

### Module types

A module's `type` decides which hosts load it:

| Type | Loaded by | Shipped in a package |
| --- | --- | --- |
| `Runtime` (the default) | every host | yes |
| `Editor` | the editor only | no |
| `Uncooked` | the editor and the cook (`mbt cook`, `mbt package`) | no |
| `ClientOnly` | everything except a dedicated server | yes |
| `ServerOnly` | a dedicated server only | yes |

`Uncooked` is the type for an importer: the editor loads it for the import dialog, and the cook host loads it to transcode source files such as `.usd` into the cooked asset, while no player or server ever carries it.

### Loading phases

A module's `loadingPhase` says when in start-up it loads. `Default` is where engine plugins have always loaded.

| Phase | Point in start-up |
| --- | --- |
| `PostConfigInit` | After command-line variables and memory, before the window, the RHI and the virtual filesystem |
| `PreDefault` | After the renderer and shaders are up, before the engine content mounts |
| `Default` | Engine plugins load, content mounts |
| `PostDefault` | After the engine's subsystems are up |
| `PostEngineInit` | After the engine finished initialising |

A dependency never loads in a later phase than the plugin that needs it: such a plugin is blocked, with the phases named in the reason. A plugin enabled after start-up loads the phases the engine already passed at once. `FPluginManager::AddLoadingPhaseListener` registers a plain function that runs after a phase completes.

### Platforms and targets

`supportedPlatforms` (`win-x64`, `linux-x64`, `osx-arm64`, `android-arm64`, `ios-arm64`) and `supportedTargets` (`Game`, `Server`, `Editor`) limit where the plugin may be live; an empty list means everywhere. A plugin outside its lists is blocked with the platform or target named, and packaging leaves it out. A module takes its own `platforms` and `targets` lists on top.

A project can also switch a plugin per platform: `Config/<Platform>/<Platform>Plugins.ini` has the same `[enabled]` section as `Plugins.ini` and wins over it when running or packaging for that platform.

### Native dependencies

A plugin that wraps a native library declares what Android and iOS must pull in, in the manifest, instead of asking every game to edit the generated projects:

```json
"nativeDependencies": {
  "android": {
    "gradle": ["com.acme:voice:2.1.0"],
    "repositories": ["https://maven.acme.example/releases"],
    "manifest": ["<uses-permission android:name=\"android.permission.RECORD_AUDIO\" />"],
    "application": ["<meta-data android:name=\"acme.key\" android:value=\"k\" />"]
  },
  "ios": {
    "pods": ["AcmeVoice", { "name": "Zlib", "version": "~> 1.2" }],
    "spm": [{ "url": "https://github.com/acme/voice-swift", "version": "3.0.0", "product": "AcmeVoice" }]
  }
}
```

`mbt package-android` adds the `gradle` coordinates and `repositories` to the app's `build.gradle`, and the `manifest` and `application` elements inside the `<manifest>` and `<application>` of `AndroidManifest.xml`. `mbt package-ios` writes a `Podfile` and a `SwiftPackageDependencies.txt` next to the staged app. Only plugins the project has enabled for that platform contribute; two plugins asking for the same library produce one entry, and a malformed coordinate or element is a manifest error.

### Trusting third-party plugins

A plugin installed from outside the engine can say what it needs in `capabilities`. Declaring a capability grants nothing: the project decides, in `Config/Plugins.ini`:

```ini title="Config/Plugins.ini"
[security]
signedOnly=true

[allowedCapabilities]
VoiceChat=network,process
```

`allowedCapabilities` lists, per plugin, the capabilities the project accepts (`*` accepts all). With `signedOnly=true`, a plugin without a signing key (`publicKey`) is flagged. The Plugins window shows the findings in amber under the plugin's name, for example "This plugin uses 'process', which this project has not allowed". Plugins that ship with the engine are exempt, and findings never stop a plugin from loading, so a warning is something to review or to turn into a check in your own pipeline.

## Enabling a plugin

Each project decides in `Config/Plugins.ini`:

```ini title="Config/Plugins.ini"
[enabled]
Combat=True
ScanHierarchy=True
```

The file wins over `enabledByDefault`. The editor's Plugins window writes it; see [Editor](/docs/editor/). Content mounts and unmounts immediately. Enabling a code plugin loads its modules at once; disabling one that is already loaded takes effect after a restart, because unloading it would remove classes that live objects use.

Cooking, packaging and the monolithic link read the same file, so a disabled plugin ships neither its content nor its binaries.

### Dependencies and versions

An enabled plugin does not load (no content, no modules) when a dependency is missing, disabled or blocked itself, when the dependencies form a cycle, or when its `engineVersion` names another engine major.minor. The plugin stays enabled, and its blocked reason appears in the log and the Plugins window:

```text
Plugin 'Survival' does not load: it requires plugin 'Combat', which is disabled
```

Modules load in dependency order: a plugin's modules load only after those of every plugin it depends on.

A dependency is a plugin name, or an object that adds a version range and an `optional` flag:

```json
"dependencies": [
  "Combat",
  { "name": "AINavigation", "version": ">=1.2 <2" },
  { "name": "SteamPlatform", "optional": true, "version": "^1" }
]
```

A range is space- or comma-separated terms that must all hold: `>=`, `>`, `<=`, `<`, `=` (or none), `^` (same major) and `~` (same major.minor), each followed by a dotted version; a pre-release suffix is ignored. A required dependency whose installed version is outside the range blocks the plugin, and the reason names both versions. An optional dependency never blocks by being absent or disabled: when it is present and enabled it loads first, and only a version outside the range blocks. Mod manifests use the same dependency form.

## Plugin config

A plugin's `Config/` folder holds INI files in the same dialect as the project's. For each config name (`Engine`, `Game`, `Input`, `Scalability`, or the plugin's own), the plugin may ship `Base<Name>.ini`, `Default<Name>.ini` and `<Platform>/<Platform><Name>.ini`. They are merged while the plugin is live, after the engine's layers and before the project's, so a plugin ships defaults for its console variables and for the `[/Script/...]` sections of its config classes, and the project's own `Default<Name>.ini` overrides them:

```text
Engine/Config/Base<Name>.ini  ->  <Plugin>/Config/*<Name>.ini  ->  <Project>/Config/Default<Name>.ini  ->  Saved/Config/...
```

A plugin switched on after the project opened rebuilds the layers before its modules load, so its classes see their own defaults. Packages stage the layers of the plugins they ship; editor-only files (names containing `Editor`) stay out.

## Runtime modules

A plugin module is an ordinary module with its own `.Build.cs`, built by `mbt` like a game module:

```csharp title="MyPlugin.Build.cs"
public class MyPlugin : ModuleRules
{
	public MyPlugin(ReadOnlyTargetRules Target) : base(Target)
	{
		PublicDependencyModuleNames.Add("EngineLoop");

		PrivateIncludePaths.Add(EngineLoopIncludeDirectory);
		CompilerFlags.Add("/FIstdafx.h");

		bUseHeaderTool = true;
		HeaderToolDirectories.Add("Public/MyPlugin");
	}
}
```

The loader looks for the module binary in the engine's binaries folder first, then in the plugin's own `Binaries/<platform>/` and `Binaries/` folders (`<platform>` is the platform id, such as `win-x64`), so a plugin can ship prebuilt. A module whose binary has not been built is skipped with a log line, and the project still opens.

Build plugins in the same configuration as the engine that loads them: the loader refuses a module built against another C++ runtime (a `debug` plugin in a `dev` editor, for example).

### Extending the engine

Reflected types (`MCLASS`, `MOWO_REFLECTED` components) register themselves when the module loads; nothing else is needed for them to save, appear in the editor and show up in Visual Scripting.

Everything else goes through `FEngineModularRegistry` from the module's `InitializeModule`: <Source symbol="FEngineModularRegistry" />

| Call | What it adds |
| --- | --- |
| `RegisterSceneSystem(FModularSceneSystem)` | An ECS scene system with its tick order and the play modes it runs in |
| `RegisterAssetSerializer(factory)` | An asset type; each host applies the registered serializers after its built-in ones |
| `RegisterStateFragment(...)` | World state a plugin system owns that save games and level travel carry |
| `RegisterCharacterExtension(...)` | Input bindings and an aim feed for a plugin-owned character mode |

These add to the engine's built-in tables and never replace them. Descriptors cross the DLL boundary as plain function pointers, never `std::function`.

Online platform plugins register an `IOnlineService` the same way; see [Multiplayer](/docs/multiplayer/).

## Editor modules

The editor is an executable with no public headers, so a plugin cannot link into it. It links **`EditorFramework`** instead, the library that holds the editor's extension points. A module of type `"Editor"` that depends on it:

```csharp title="MyPluginEditor.Build.cs"
public class MyPluginEditor : ModuleRules
{
	public MyPluginEditor(ReadOnlyTargetRules Target) : base(Target)
	{
		PrivateDependencyModuleNames.Add("Core");
		PrivateDependencyModuleNames.Add("Arc");
		PrivateDependencyModuleNames.Add("EditorFramework");
	}
}
```

Two registries are available:

- **`FEditorDockPanelRegistry`** registers dock panels. A panel appears under **Window > Plugins** and restores with the layout like a built-in one. <Source symbol="FEditorDockPanelRegistry" />
- **`FEditorExtensionRegistry`** adds menu entries (File, Edit, Tools, Window, Build, Help; entries that name the same `Group` share a submenu), toolbar buttons beside the play controls, Content Browser asset actions (rows in an asset's context menu), Details customizations keyed by component type, and viewport modes. <Source symbol="FEditorExtensionRegistry" />

```cpp title="MyPluginEditor.cpp"
#include <Arc/Framework/ArcDeclarativeSyntax.h>
#include <Arc/Widgets/ATextBlock.h>
#include <Core/FModuleManager.h>
#include <EditorFramework/EditorExtensionRegistry.h>
#include <EditorFramework/EditorPanelRegistry.h>

#include <utility>

MOWO_IMPLEMENT_MODULE_API_VERSION()

extern "C" MOWO_MODULE_EXPORT void InitializeModule() {
	Mowo::FEditorDockPanelDesc panel;
	panel.Kind = "MyTool";
	panel.Title = "My Tool";
	panel.Create = [](int32_t) {
		Mowo::FEditorDockPanelInstance instance;
		instance.Surface = ArcNew(Arcf::ATextBlock).Text(Arcf::CText::FromString("Hello from MyPlugin"));

		return instance;
	};
	Mowo::FEditorDockPanelRegistry::Get().Register(std::move(panel));

	Mowo::FEditorMenuExtension entry;
	entry.Id = "MyPlugin.Run";
	entry.Menu = Mowo::EEditorMenu::Tools;
	entry.Label = "Run My Tool";
	entry.Execute = []() {
	};
	Mowo::FEditorExtensionRegistry::Get().AddMenuEntry(std::move(entry));
}

extern "C" MOWO_MODULE_EXPORT void ShutdownModule() {
	Mowo::FEditorExtensionRegistry::Get().RemoveMenuEntry("MyPlugin.Run");
	Mowo::FEditorDockPanelRegistry::Get().Unregister("MyTool");
}
```

<Callout type="warning">
Remove in `ShutdownModule` everything you added in `InitializeModule`. A panel factory, a menu callback and every widget they built are code inside your DLL; an entry left behind is called or destroyed after that code is gone.
</Callout>

### Settings pages, asset actions and new assets

A plugin with its own asset type or settings registers them with **`FEditorPluginExtensions`**. Everything is plain data and plain function pointers, and the registry remembers which module added an entry and drops it when that module unloads. <Source symbol="FEditorPluginExtensions" />

| Call | What it adds |
| --- | --- |
| `AddSettingsPage` | A page in Project Settings or Editor Preferences, under **Plugins**. Name an `MCLASS` with `ConfigClass` and the page lists its `MPROPERTY(Config)` fields and writes the project's `Config/DefaultGame.ini`, or give a `Build` function for a page of your own |
| `AddAssetAction` | An entry in the Content Browser's right-click menu for the asset extensions you list |
| `AddNewAssetEntry` | An entry in the Content Browser's **New asset** menu; the browser picks a unique name and calls your `Create` to write the file |

An importer needs none of this: register the translator with `FImportTranslatorRegistry::Get().Register(...)` and it is removed when the module unloads.

## The module ABI check

Every module binary exports its ABI version with `MOWO_IMPLEMENT_MODULE_API_VERSION()` from `Core/FModuleManager.h`. Right after loading a library, `FModuleManager` compares it with the engine's `MOWO_MODULE_API_VERSION` and the C++ runtime the module was built against. A binary that exports another number, or none, is refused: the log names the module and says to rebuild it against this engine, its static registrations are removed, and the library is freed. <Source symbol="FModuleManager::LoadModule" />

The check exists because descriptors such as `FModularSceneSystem` are copied with the engine's layout; a plugin built against an older layout would hand over a shorter struct. When you change such a boundary type in the engine, bump `MOWO_MODULE_API_VERSION`.

## Unloading

When a project closes, its plugin modules unload. The world is torn down first, then each module's reflected classes are unregistered, a garbage collection frees objects whose code lives in the module, `ShutdownModule` runs, and the library is freed.

Before the library is freed, the engine sweeps every registry that might still point into it: scene systems, reflection, the modular registry, console commands, property-type handlers, `EventBus` subscriptions, timers and others. Most registrations record the module they came from automatically, so plugin code needs no extra step. `FModuleManager::AddUnloadHandler` lets your own registries join the sweep.

## Shaders

A plugin keeps HLSL in `Shaders/` and maps it to a virtual root in its `.Build.cs`:

```csharp
AddShaderSourceDirectoryMapping("/Plugin/MyPlugin", "Shaders");
ShaderDirectories.Add("Shaders/Private");
ShaderArchive = "MyPluginShaders.meaf";
```

Its shaders include engine headers as `/Engine/Public/…` and their own as `/Plugin/MyPlugin/…`, and their compiled keys carry the `Plugin/MyPlugin/` prefix, so a plugin cannot replace an engine shader. See [Rendering](/docs/rendering/).

## Content and packaging

An enabled plugin's `Content/` mounts at `Plugins/<Name>`, so its assets are referenced as `Plugins/MyPlugin/Materials/M_Plastic.mat`. Cooking and packaging put every enabled plugin's content into the game's content archive under the same prefix, so references resolve unchanged in a packaged game. See [Shipping](/docs/shipping/).

## Engine plugins and feature modules

Engine systems such as AI and navigation, the Sequencer and destruction are feature modules. They build with the engine, but a project switches each one in `Config/Plugins.ini` exactly like a plugin, and the Plugins window lists them under **Engine Features**. A game loads, registers and packages only the ones its project enables; the editor registers all of them, because its asset editors open every asset type, and the switch decides what a standalone run, the packaged game and the server load. Play in the editor keeps every module registered.

| Feature module | Default | Needs |
| --- | --- | --- |
| `AINavigation` (AI and Navigation) | on | |
| `Narrative` | on | AINavigation |
| `VoiceChat` | off | |
| `Destruction`, `GeometryTools`, `PointCloud`, `Sequencer`, `LevelGen`, `PCG`, `GpuEcs` | off | |
| `Accessibility` (Automatic Subtitles, ONNX Runtime) | off | VoiceChat, Narrative |

AI and Navigation and Narrative are on because the templates place navigation agents, schedules, quests and music, and Combat depends on both. A plugin may name a feature module in `dependencies` (Combat does), and turning that module off blocks the plugin. What stays a plugin is what a game opts into on top: platform SDKs (SteamPlatform, DiscordPlatform, MowoOnlinePlatform), gameplay kits (Combat, Survival), SmartProps and ScanHierarchy. No engine module depends on a plugin. See [Architecture](/docs/getting-started/core-concepts/#feature-modules).

```ini title="Config/Plugins.ini"
[enabled]
VoiceChat=True
Sequencer=True
AINavigation=False
```

A module another enabled module links stays loaded by the operating system but does not register: Narrative links VoiceChat, so its library is mapped, yet with VoiceChat off no voice system, input action or setting exists. The package carries `Config/Plugins.ini` and stages only the enabled modules, so a monolithic game compiles in and registers exactly that set.

## What a machine skips

At startup the engine probes the machine once and logs a `[Capabilities]` block: CPU, audio devices, gamepads, whether the Steam and Discord clients run, the GPU, driver and VRAM, hardware ray tracing, mesh shaders, VRS, bindless, async compute, and each vendor feature with the reason it is missing. Vendor features are decided from the vendor, model and driver: DLSS needs an NVIDIA RTX GPU and driver 520 or newer, DLSS Frame Generation an RTX 40-series, Reflex any NVIDIA GPU, Anti-Lag 2 a Radeon RX, XeSS Frame Generation and XeLL an Intel Arc GPU; FSR and XeSS run on every vendor. No vendor runtime loads to answer, and a runtime this GPU cannot run never loads.

A `[Features]` block follows: every subsystem that waits for a capability, a project switch or an enabled module, and whether it starts. A skipped one allocates nothing and starts no thread:

```text
[Features] skipped VoiceCapture: no audio input device
[Features] skipped SteamOnline: the Steam client is not running
[Features] skipped DLSS Frame Generation runtime: needs an RTX 40-series or newer
```

The client check runs once at startup: a Steam or Discord client started after the game is picked up on the next launch.
