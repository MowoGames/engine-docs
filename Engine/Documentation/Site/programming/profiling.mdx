The profiling tools work the same in the editor, a development game and a dedicated server. There is no separate profiling build. Start with `stat unit` to see where a frame goes, then narrow down with counters, a capture or a trace.

## stat commands

Type them in the editor's Output Log console or the game console, or call `IConsoleManager::Get().Execute("stat unit")` from code.

| Command | Shows |
| --- | --- |
| `stat fps` | Frame rate and mean frame time |
| `stat unit` | The frame, game, draw, RHI and GPU times |
| `stat unitgraph` | The last 240 frames of the unit times as four lines (frame, game, draw, GPU) against the frame budget |
| `stat gpu` | Per-pass GPU times from the last resolved frame |
| `stat memory` | Live bytes per memory tag (needs a `--memtrack` build) |
| `stat hitches` | Frame-time percentiles and hitch counts |
| `stat hardware` | CPU and GPU load, clocks, temperature, power, throttling, VRAM and process memory ([Hardware telemetry](/docs/programming/telemetry/)) |
| `stat net` | Ping, jitter, packet loss, bandwidth and the server tick |
| `stat <group>` | A stat group's cycle counters as a table |
| `stat none` | Hides every display |
| `stat list` | Logs every group and counter |
| `stat dump` | Logs the counters that recorded something last frame |
| `stat enable <group>`, `stat disable <group>` | Turns a group's measurement on or off |
| `stat startfile [path]`, `stat stopfile` | Writes one CSV row per frame: frame number, time and deltas |

 The stat displays are text over the scene with a drop shadow, never on an opaque background. These console variables change how they sit: `stat.Corner` (0 top right, 1 top left, 2 bottom right, 3 bottom left; at the bottom right the block stacks above `net.graph`), `stat.Opacity` (0.2 to 1), `stat.Background` (0 by default; above 0 draws a plate of that alpha), `stat.TextStyle` (0 shadow, 1 outline) and `stat.Compact` (1 collapses `stat fps` and `stat unit` to one line). `ui.DebugOverlays.Hide 1` hides the stats and the on-screen messages for a capture. In the editor the block sits inside the viewport, under its toolbar, during Play as well. The display commands toggle, so typing `stat fps` twice turns it off. Values are coloured against the frame budget (16.67 ms by default, `FFrameStats::SetBudgetMs`): amber past it, red past twice it. Hitches are counted at 1.5×, 2× and 4× the budget.

### What stat unit measures

| Row | Span |
| --- | --- |
| `frame` | The whole loop iteration |
| `game` | `Tick`: gameplay, systems, scene update |
| `draw` | Everything after `Tick`: `Draw`, the overlay, submission and present |
| `rhi` | Frame setup before `Tick` |
| `gpu` | GPU time of the last resolved frame; `n/a` when the backend has no timers |

`stat.FrameStats <N>` logs averaged CPU stage times and the GPU frame time every N frames, without the overlay.

## Cycle counters

Stat groups are declared in `Core/EngineStats.h`: `Game`, `Render`, `RHI`, `Physics`, `Audio`, `Animation`, `AI`, `UI`, `Particles`, `Network` and `Asset`. Counters live with the code they measure: <Source path="Engine/Source/Runtime/Core/Public/Core/EngineStats.h" />

```cpp
#include "Core/EngineStats.h"

MOWO_DEFINE_LOCAL_CYCLE_STAT(SpawnWave, AI);

void SpawnWave() {
	MOWO_SCOPE_CYCLE_COUNTER(SpawnWave);
}
```

To share a counter between files, declare it in a header with `MOWO_DECLARE_CYCLE_STAT(MYGAME_API, TickAI, AI)` and define it in one `.cpp` with `MOWO_DEFINE_CYCLE_STAT_API(MYGAME_API, TickAI, AI)`. A scope records inclusive time, self time and a call count, per thread. With its group disabled a scope costs one atomic load.

`MOWO_PROFILE_SCOPE("Name")` marks a profiler zone instead; zones feed Tracy, the CSV profile, the editor's Profiler panel and traces.

## Per-zone CSV capture

`--csvprofile=<file>` writes one row per frame and one column per profiler zone (the summed milliseconds of every zone of that name), after `frame,frameMs,gpuMs`. Diff two captures zone by zone to find a regression.

The capture turns on the profiler, which takes a lock per scope and changes thread timing. Judge timing-sensitive crashes from a run without it.

## Tracy

Tracy is compiled in by default in `dev` and `profile` builds on Windows and macOS, idle until a viewer connects. Elsewhere it is opt-in with `-o MOWO_ENABLE_TRACY=true`, and `=false` turns the default off. Run `tracy-profiler` on the same machine and connect to the running game or editor. The client listens on loopback only, so it opens no port to the network and the viewer must run locally.

On Direct3D 12 and Vulkan the GPU zones sit where the GPU ran them, not at the CPU's frame begin: the timers read the device's calibrated clock pair and walk back to the frame's first timestamp, so a deep frame queue no longer shifts every GPU zone by the frames in flight. Other backends place them at the CPU frame begin.

Game code profiles with the macros in `Core/Profiler.h` and never includes a Tracy header: the engine hosts the one Tracy client and the macros reach it through functions it exports, so a game module built against the installed engine compiles and records zones the same way. Where Tracy is compiled out, so is the Tracy half of every macro; zones still feed the CSV profile, the Profiler panel and traces. <Source path="Engine/Source/Runtime/Core/Public/Core/Profiler.h" />

```cpp
#include "Core/Profiler.h"

void AWaveSpawner::Tick(float deltaTime) {
	MOWO_PROFILE_FUNCTION();
	MOWO_PROFILE_PLOT("Waves/Alive", static_cast<int64_t>(m_alive.size()));
}
```

| Macro | Records |
| --- | --- |
| `MOWO_PROFILE_SCOPE(name)`, `MOWO_PROFILE_FUNCTION()` | A zone until the end of the scope; the name may be a runtime string |
| `MOWO_PROFILE_RENDER(name)`, `_PHYSICS`, `_AUDIO`, `_SCRIPT`, `_INPUT`, `_SCENE`, `_ASSET`, `_UI`, `_ECS`, `_MEMORY` | A zone in that category's colour |
| `MOWO_PROFILE_PLOT(name, value)` | A value over time; `value` is an `int64_t`, `double` or `float` |
| `MOWO_PROFILE_MESSAGE(text, size)`, `MOWO_PROFILE_MESSAGE_L(literal)` | A message on the timeline |
| `MOWO_PROFILE_ALLOC(ptr, size)`, `MOWO_PROFILE_FREE(ptr)` | An allocation and its free, for Tracy's memory view |
| `MOWO_PROFILE_MUTEX(name, description)` | A mutex member Tracy draws on its lock timeline; lock it as `std::lock_guard<Mowo::FProfiledMutex>` |

## Whole-run traces

A trace records every frame of a run (CPU scopes per thread, GPU passes, memory tags and the `stat unit` phases) to a `.mtrace` file you open afterwards:

```bash
MowoGame.exe --trace=Saved/Profiling/Run.mtrace
```

`--trace=<file>` sets the `mowo.Trace.File` console variable at start-up; setting it from the console starts a trace mid-run, and setting it empty stops it. A writer thread encodes the frames, so the game thread only queues them; if the writer falls behind, frames are counted as dropped instead of stalling the game. Past `mowo.Trace.MaxSizeMB` (2048 by default) the trace continues in `Run_001.mtrace`, `Run_002.mtrace` and so on. A trace from a process that crashed keeps every whole frame before the crash.

Publish your own per-frame numbers with `FTraceWriter::Get().SetCounter("DrawCalls", n)`; MowoInsights plots them.

### Watching a trace live

Set `mowo.Trace.Port` to a port before the trace starts and the process also serves the trace on that loopback port while it writes the file (`FTraceStreamServer` in `Core/TraceStream.h`). A viewer that joins late gets the part header and the name tables first, so what it holds is a valid trace. A viewer that cannot keep up is dropped instead of slowing the game; when the file rotates to a new part, the live view follows the newest part.

```bash
MowoGame.exe --trace=Saved/Profiling/Run.mtrace --cvar=mowo.Trace.Port=1980
MowoInsights.exe --connect=127.0.0.1:1980
```

### Profiling a device from another machine

The live port listens on loopback only, so a handheld such as the Steam Deck cannot be reached from the desktop by default. There are two ways to open it up, and both take IPv4 addresses.

Bind to the network with `mowo.Trace.Bind` (`--trace-bind=<address>`). `0.0.0.0` listens on every interface, and anyone on that network can then read the trace, so use it on a network you trust.

```bash
MowoGame --trace=Saved/Profiling/Run.mtrace --cvar=mowo.Trace.Port=1980 --trace-bind=0.0.0.0
MowoInsights.exe --connect=192.168.1.40:1980
```

Or let the game dial the viewer with `--trace-to=<host>:<port>` (`mowo.Trace.To`). The viewer listens, the game connects out, so this works through NAT and a firewall that blocks inbound connections. The game redials every couple of seconds while no viewer is connected, and a viewer that restarts picks the stream up again with the part header and name tables. Without `--trace` the trace file defaults to `Saved/Profiling/Remote.mtrace`. `--trace-to` replaces `mowo.Trace.Port` when both are set.

```bash
MowoInsights.exe --listen=1980
MowoGame --trace-to=192.168.1.20:1980
```

A host name is not resolved; pass the viewer machine's IPv4 address. While the game is dialing an unreachable address, shutting the trace down can wait for the connection attempt to time out.

## MowoInsights

MowoInsights is the standalone viewer for `.mtrace` traces and `.mprof` captures, the equivalent of Unreal Insights. It needs no editor and no project.

```bash
./mbt.cmd build -t MowoInsights
MowoInsights.exe Saved/Profiling/Run.mtrace
MowoInsights.exe --open=Run.mprof
```

You can also drop a file on the window or use **Open…**; **Reload** rereads a trace that is still being written.

<Screenshot id="programming-insights-window" alt="MowoInsights with a .mtrace open: the frame graph at the top with one red spike selected, the timeline lanes for the game thread, render thread and GPU below it, and the scope tree on the side." caption="MowoInsights with a spike selected." />

- **Frames:** every frame as a bar against the budget line, spikes marked in red. When there are more frames than pixels, each column shows the slowest frame it covers.
- **Timeline:** the selected frame's lanes, one per CPU thread and one for the GPU. **Next spike** jumps to the next spike; **Fit** resets the zoom.
- **Scope tree:** inclusive and self milliseconds and call counts for the selected frame.
- **Hot list:** every scope summed over the trace, sorted by self time.
- **Counters:** frame, game, draw and GPU times and every published counter, plotted over the trace.

### Querying a trace without the window

`--query` prints the answer as text and exits, for scripts and CI. The trace is a path, `--open=<path>` or a live `--connect=host:port` read for `--seconds=N` (default 2).

```bash
MowoInsights.exe --query=summary Run.mtrace
MowoInsights.exe --query=scopes --sort=inclusive --top=10 --match=physics Run.mtrace
MowoInsights.exe --query=memory --out=memory.txt Run.mtrace
```

| `--query=` | Prints |
|---|---|
| `summary` | Frame count and span, frame-time average and percentiles, frames over budget, dropped frames |
| `scopes` | CPU scopes summed over the trace; `--sort=self\|inclusive\|max\|calls` |
| `counters` | Every counter's first, last, minimum, maximum and average |
| `memory` | Per memory tag the live bytes at the start and end, the growth and the peak, largest growth first: a tag that only climbs is a leak |
| `frames` | The slowest frames with their lane timings |
| `allocations` | The allocation track of a trace recorded with `mowo.Trace.Allocations` (see below): allocated, freed and live bytes per tag, and the largest blocks never freed |

`--first-frame` and `--last-frame` narrow the range, `--match` filters names, and `--out=<file>` also writes the text to a file. `memory` needs a trace recorded with memory tracking (see [Memory](#memory)).

## Retained frames in the editor

The editor's Profiler panel keeps a ring of recent frames you can scrub after a spike has passed, and saves it as `.mprof`. The ring is disarmed until the panel records, because copying every scope each frame has a cost. In a game or on a server, `mowo.Profiler.Capture 1` arms it. See [Editor](/docs/editor/).

## Memory

`stat memory` reads the memory tracker, which is compiled out of normal builds. Build with `mbt build --memtrack` to get live bytes, peak and allocation counts per tag. Tag your own allocations with `MOWO_LLM_SCOPE(tag)`.

### Allocation tracks in a trace

A trace can also record when large blocks are allocated and freed, so MowoInsights can show which tag's memory keeps climbing and which blocks were never freed. It is off by default:

```bash
MowoGame.exe --trace=Saved/Profiling/Run.mtrace --cvar=mowo.Trace.Allocations=1 --cvar=mowo.Trace.AllocMinBytes=16384
MowoInsights.exe --query=allocations --top=15 Saved/Profiling/Run.mtrace
```

`mowo.Trace.Allocations` is read when the trace starts. Only allocations of at least `mowo.Trace.AllocMinBytes` (4096 by default) are recorded, one in `mowo.Trace.AllocSample` of them (1 = all), and a free is recorded only for a block whose allocation was. The numbers are therefore lower bounds, and the query says how many events the queue dropped. Events go through the engine heap (`FMemory`), so a build with `--no-mimalloc` or `--asan` records none. Blocks carry the tag of the innermost `MOWO_LLM_SCOPE`, which needs a `--memtrack` build; without it every block is `Unknown`.

The Counters view of MowoInsights plots three extra series, `Alloc.Traced.AllocatedBytes`, `Alloc.Traced.FreedBytes` and `Alloc.Traced.LiveBytes`, one value per frame.

What it costs:

- Off: one relaxed atomic load per allocation and per free, plus about 5.6 MB of static memory in `MowoEngine.Core` that is never touched.
- On, for a block below the minimum: that load, a size comparison and an atomic read of the threshold.
- On, for a recorded block: a few atomic operations, a probe of a fixed 2 MB table of live pointers and a 56-byte slot in a 64K-event queue, in the order of tens of nanoseconds. A thread that finds the queue full drops the event instead of waiting.
- The trace writer thread drains the queue and wakes every 50 ms to do so; its own allocations are not recorded.

Measure it on your game with a trace of the same scene with and without it before relying on the frame times of the run that records.
