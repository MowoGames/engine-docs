Every `mbt` command returns a small, fixed set of exit codes, so scripts and CI jobs can tell a failed build from a mistyped command. The wrapper scripts pass the code through unchanged <Source path="mbt.cmd" />.

## The codes

| Code | Meaning | Typical causes |
|---|---|---|
| `0` | Success | The command did what it was asked |
| `1` | The work failed | Compile or link errors, failing tests, a required tool missing in `doctor`, a failed cook or package step, stale output under `docs --check` |
| `2` | Usage or setup problem, or an incomplete result | No engine checkout found, an invalid option value, a contradictory pair of options, a bad `--project` path, a Shipping package without content keys; `test` cases skipped |
| `3` | Shader compiler not found | DXC is missing when shaders must compile |

## 1: the work failed

The command ran and the result was a failure. `build` returns 1 when any module fails to compile or link, or when a rules file does not compile <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/BuildCommand.cs" />. `doctor` returns 1 when a required tool is missing <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/DoctorCommand.cs" />. `test` returns 1 when any case failed. `package` returns 1 when a step fails, for example a cook error, a monolithic import check, or a Shipping symbol upload that was attempted and failed <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/PackageCommand.cs" />.

<Callout type="note">
A missing or too old C++ toolchain also ends `build` with 1: toolchain detection fails the build rather than returning a code of its own. Run `mbt doctor` to see what is missing.
</Callout>

## 2: the command could not run as asked

`mbt` returns 2 before doing any work when, for example:

- it cannot find an engine checkout above the current directory ("No MowoEngine checkout found");
- `--platform`, `--targets` or `package --target` has an unknown value;
- `--hot-reload` or `--frozen-engine` is passed without `-t`, or two sanitizers are combined;
- `package` gets both `--monolithic` and `--modular`, a mobile platform, or an output folder that is not empty and does not look like an earlier package;
- `--project` does not point at an existing `.mproject`;
- a Shipping package's project has no content keys and `--unprotected` was not passed.

`test` also uses 2 for an incomplete run. If any case was skipped, the run exits 2 unless you pass `--allow-skips`, so a partial run never reads as a full one <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/TestCommand.cs" />.

## 3: shader compiler not found

`shaders`, `package`, `package-editor` and `package-android` return 3 when DXC cannot be found <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/ShadersCommand.cs" />. The vendored copy is expected at `Engine/Binaries/ThirdParty/DXC/<Host>/`; `$VULKAN_SDK/Bin` and `PATH` are fallbacks <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Shaders/ShaderCompiler.cs" />. On a fresh checkout this usually means the Git LFS content is missing.

## Using exit codes in scripts

<CodeTabs>

```powershell tab="PowerShell"
.\mbt.cmd build -c Development
if ($LASTEXITCODE -ne 0) {
    Write-Error "Build failed with exit code $LASTEXITCODE"
    exit $LASTEXITCODE
}

.\mbt.cmd test --cpu-only --allow-skips
```

```bash tab="bash"
./mbt.sh build -c Development || exit $?

./mbt.sh test --cpu-only
status=$?
if [ "$status" -eq 2 ]; then
    echo "Some test cases were skipped"
fi
```

</CodeTabs>

<Callout type="tip">
On a machine without a GPU, `mbt test --cpu-only` skips the device cases. Add `--allow-skips` if skipped cases should not fail the job, and keep it off where full coverage is expected.
</Callout>

## Codes from the wrapper

If `mbt.cmd` cannot publish the build tool, it exits 1 before your command runs and prints `[mbt] FAILED to publish MowoBuildTool`. It does the same when the publish reports success but left an older `mbt.exe` in place, usually because a running `mbt` or an IDE holds the file. Close the holder and run the command again.

Exit codes of individual test processes, such as 77 for a skipped case, belong to the test executables; see [Testing](/docs/testing/).
