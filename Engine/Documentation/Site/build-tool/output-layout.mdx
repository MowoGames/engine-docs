Every build writes into two folders of the checkout: `Engine/Binaries/` for what runs, and `Engine/Intermediate/Build/` for objects and generated code. Each configuration gets a folder of its own, and file names carry only the name, so two configurations never share a folder and a file never has to be told apart by a suffix.

## Platform ids

Every folder that holds platform-specific files is named with a platform id <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Utils/EngineLayout.cs" />:

| Platform | Id |
|---|---|
| Windows x64 | `win-x64` |
| Linux x64 | `linux-x64` |
| macOS arm64 | `osx-arm64` |
| Android arm64 | `android-arm64` |
| iOS arm64 | `ios-arm64` |

`mbt --platform` takes the ids; the older selectors (`win64`, `linux`, `macos-arm64`, `android`, `ios`) still work. At run time `PlatformName()` returns the same id.

## Binaries

Executables and module libraries land in `Engine/Binaries/<platform>/<config>[-<variant>]/`, where `<config>` is `debug`, `dev`, `profile`, `release` or `debuggame` <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Modules/BinaryLayout.cs" />:

| Build | Folder | Executable |
|---|---|---|
| `mbt build -c dev -t MowoEditor` | `Engine/Binaries/win-x64/dev/` | `MowoEditor.exe` |
| `mbt build -c debug -t MowoGame` | `Engine/Binaries/win-x64/debug/` | `MowoGame.exe` |
| `mbt build -c release -t MowoGame` | `Engine/Binaries/win-x64/release/` | `MowoGame.exe` |
| `mbt build -c dev -t MowoEditor` on Linux | `Engine/Binaries/linux-x64/dev/` | `MowoEditor` |
| `mbt build -c dev -t MowoEditor` on macOS | `Engine/Binaries/osx-arm64/dev/` | `MowoEditor` |

An executable is its name with the platform's extension: `MowoEditor.exe`, `MowoGame.exe`, `MowoServer.exe`, `MowoProjectLauncher.exe`, `MowoCrashReporter.exe`, `CoreTests.exe`, and no extension on Linux and macOS. A module library is its run-time module name: `MowoEngine.Core.dll`, `libMowoEngine.Core.so`, `libMowoEngine.Core.dylib`, `MowoEngine.dll` for the engine loop, `MowoEngine.Plugins.SteamPlatform.dll` for a plugin. On Android the one image keeps the name its loader asks for: `Engine/Binaries/android-arm64/dev/libmain.so`.

The C++ side finds a module's file at run time through `Platform/BinaryNames.h`. The only identifier `mbt` passes for it is `MOWO_BINARY_PLATFORM` (`win_x64`, `linux_x64`, …) <Source path="Engine/Source/Runtime/Platform/Public/Platform/BinaryNames.h" />.

### Variant folders

A build whose every image differs from the default one adds a suffix to the configuration folder, so it never overwrites the default binaries. Suffixes come in this order: target tree, sanitizer, analysis, link type.

| Build | Folder |
|---|---|
| The dedicated server (`bSeparateOutputTree`) | `dev-server/` |
| `MowoGameNoOnline` | `dev-noonline/` |
| The games launcher | `release-gameslauncher/` |
| `--asan`, `--ubsan`, `--tsan` | `debug-asan/`, `debug-ubsan/`, `debug-tsan/` |
| `--analyze` | `dev-analyze/` |
| Monolithic in `debug`, `dev` or `debuggame` | `dev-monolithic/` |
| Modular in `release` or `profile` | `release-modular/`, `profile-modular/` |

A separate tree is named after its target without `Mowo` (or without `MowoGame` before a variant word), lowercased <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/TargetRules.cs" />.

### Beside the binaries

The build packs the engine's archives into each configuration folder, next to the executables <Source path="Engine/Source/Runtime/EngineLoop/EngineLoop.Build.cs" />. Every configuration folder has its own copy, and `mbt shaders -c <config>` packs into that folder.

| File | Contents |
|---|---|
| `Shaders.meaf` | The engine's compiled shaders |
| `StandaloneShaders.meaf` | The UI shaders small tools draw with <Source path="Engine/Source/Runtime/Arc/Arc.Build.cs" /> |
| `EngineContent.meaf` | `Engine/Content` |
| `MLModels.meaf` | The machine-learning models the editor uses <Source path="Engine/Source/Runtime/ML/ML.Build.cs" /> |

`Content/` and `Resources/` sit there too. Vendor runtime files (SDL3, the D3D12 Agility SDK in `D3D12/`, Steam, upscalers, ONNX Runtime and its WebGPU execution provider) are staged beside the modules that need them. On Windows the WebGPU provider gets the engine's DXC 1.9 (`dxcompiler.dll`, `dxil.dll`) beside it, because the provider's GPU backend loads DXC from its own folder <Source path="Engine/Source/ThirdParty/OnnxRuntimeWebGpu/OnnxRuntimeWebGpu.Build.cs" />. A binary finds the engine root from its own path, not the working directory, so you can start it from anywhere <Source path="Engine/Source/Runtime/Core/Public/Core/FPaths.h" />.

### The modules manifest

Every target built into one folder shares that folder's module libraries. A build of one target can therefore replace a library that another target's executable was compiled against, for example a `MowoProjectLauncher` build relinking `MowoEngine.Arc.dll` after a header change, while `MowoEditor.exe` in the same folder still has the old layout of the types the two share. To catch this, a modular build writes `MowoEngine.modules` into each binaries folder it links into, as Unreal Engine does with its `.modules` files <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Modules/ModulesManifest.cs" />.

Each executable and module library carries a build id, an exported `MowoImageBuildId` string that `mbt` compiles in right before each link. The id is a hash of the link's inputs, so a deterministic configuration still produces identical files from identical inputs <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Build/ImageBuildId.cs" />. For every image, the manifest records its id, the target that built it, and the ids of the images in the same folder it was built against. A build rewrites only the entries of the images in its own closure. Images it did not touch keep the record of what they were built against.

At startup, Core checks the executable and every module of its folder that it has mapped. Modules loaded later by name (feature modules, plugins, game modules) are checked by the module manager before they are mapped <Source symbol="FBuildManifest" />. A process is refused, with a message that names the file and the command that rebuilds it, when:

- the file is not in the manifest,
- the file carries no build id, or a different one than the manifest records (it was replaced, copied in, or left behind by an interrupted link),
- a module it was built against has been rebuilt since, or is gone.

```text
Mowo: modules from another build: Refusing to start. MowoEditor.exe was built against MowoEngine.Arc.dll build 1f0c…, but MowoEngine.Arc.dll has since been rebuilt (build 9a42…, by a build of MowoProjectLauncher). … Rebuild MowoEditor.exe: ./mbt.cmd build -t MowoEditor -c dev
```

The process exits with code 78. The build that makes another target's binaries stale also prints a warning that lists them and the commands that rebuild them. Set `MOWO_IGNORE_BUILD_ID=1` to run anyway; the process then prints the problem and continues.

- A monolithic build has nothing to check and writes no manifest.
- A modular package ships a manifest of its own, with the entries of the staged files under the names the package gives them. The installed editor build keeps the entries of the files it ships.
- A hot-reload build links a new versioned file (`<Module>.v<N>.dll`) and records it like any other image, so loading it passes the check. Live Coding patches code in memory and does not load modules through the module manager.
- A folder without a manifest, such as a tree built before manifests existed, is not checked.

## Intermediates

| Path | Contents |
|---|---|
| `Engine/Intermediate/Build/<platform>/<config>[-<variant>]/<Module>/Obj/` | Object files |
| `Engine/Intermediate/Build/<platform>/<config>[-<variant>]/<Module>/Deps/` | Dependency files |
| `Engine/Intermediate/Build/Generated/<config>/<Module>/` | Generated code, including the header tool's output in `Reflection/` |
| `<Project>/Intermediate/Build/<config>/<Module>/Generated/` | A project module's generated code, kept with the project |

An intermediate folder has the same name as its binaries folder (`win-x64/dev-server`, for example); there is no environment folder. <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/ModuleScopes.cs" /> defines these paths. Everything under `Engine/Intermediate/` is disposable.

`mbt` keeps its own state in `.mbt-cache/` at the engine root: a `build.db` of compile fingerprints per output tree, and `Rules/` with the compiled rules assemblies. `mbt clean` invalidates the fingerprints before it removes build output, so an interrupted clean only makes the next build rebuild more.

## Third-party files

| Path | Contents |
|---|---|
| `Engine/Source/ThirdParty/<Lib>/` | Headers, the library's `.Build.cs`, its license |
| `Engine/Source/ThirdParty/<Lib>/Lib/<platform>/` | Static and import libraries |
| `Engine/Binaries/ThirdParty/<Lib>/<platform>/` | Runtime files and tools: DLLs, DXC, spirv-cross, astcenc, dump_syms, sentry-cli, ONNX Runtime and the ONNX Runtime WebGPU execution provider |

<Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Utils/EngineLayout.cs" /> owns these fixed paths.

ONNX Runtime follows the same split: on Windows its import library is `Engine/Source/ThirdParty/OnnxRuntime/Lib/win-x64/onnxruntime.lib` and `onnxruntime.dll` sits in `Engine/Binaries/ThirdParty/OnnxRuntime/win-x64/`; on Linux and macOS the shared library is in `Engine/Binaries/ThirdParty/OnnxRuntime/linux-x64/` and `.../osx-arm64/` <Source path="Engine/Source/ThirdParty/OnnxRuntime/OnnxRuntime.Build.cs" />. The WebGPU provider is in `Engine/Binaries/ThirdParty/OnnxRuntimeWebGpu/<platform>/`. Nothing links it: the engine loads it at run time, so a missing copy leaves inference on the CPU.
