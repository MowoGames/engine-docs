The build is described by two kinds of C# file, shaped like Unreal Build Tool's. A **module** (`<Module>.Build.cs`) is a unit of code: one folder of sources that builds into one library. A **target** (`<Target>.Target.cs`) is one executable: which module it launches, what kind of binary it is, and the definitions every module in it compiles with.

This page is the reference for both files. For a game project's own module, start with the [programming section](/docs/programming/), which walks through it from a game programmer's side.

## A module

```csharp title="Engine/Source/Runtime/GameHost/GameHost.Build.cs (excerpt)"
public class GameHost : ModuleRules
{
	public GameHost(ReadOnlyTargetRules Target) : base(Target)
	{
		PublicDependencyModuleNames.Add("EngineLoop");
		PublicDependencyModuleNames.Add("Arc");
		PublicDependencyModuleNames.Add("ArcUI");

		DynamicallyLoadedModuleNames.AddRange(new[] { "AINavigation", "GeometryTools", "PointCloud", "Sequencer", "PCG", "GpuEcs" });

		if (Target.bWithOnline)
		{
			DynamicallyLoadedModuleNames.AddRange(new[] { "Destruction", "Narrative", "VoiceChat", "LevelGen" });
		}
	}
}
```

The file is named after the module, declares a class of the same name deriving from `ModuleRules`, and takes a `ReadOnlyTargetRules` in its constructor <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/ModuleRules.cs" />. A name C# cannot spell has those characters turned into `_` (`metal-cpp.Build.cs` declares `metal_cpp`). A misnamed class, a rules file that does not compile, and two modules of the same name in one scope stop the build <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/RulesAssembly.cs" />.

### What the folders already say

Folders replace most lines:

| Convention | Effect |
|---|---|
| `Public/`, `Classes/` | Public include paths: every module that depends on this one sees them |
| `Private/` | The sources, and a private include path |
| `Internal/` | Visible to modules of the same scope only |
| A folder named after another platform (`Windows/`, `Linux/`, `Mac/`, …) | Skipped when building for a different platform |
| The module's place in the binaries | `MOWO_BUILD_<MODULE>` (private) and `MW_DYNAMIC_LINK` (public), which switch its export macro |
| New `.cpp` files | Picked up without editing anything |

Dependencies use short names (`"Core"`, `"EngineLoop"`). An engine library's run-time name stays `MowoEngine.<Name>`, which is what plugin manifests and the module manager use.

### Common fields

| Field | Meaning |
|---|---|
| `PublicDependencyModuleNames` | Linked, and their public headers re-exported to this module's dependents |
| `PrivateDependencyModuleNames` | Linked, headers visible to this module only |
| `DynamicallyLoadedModuleNames` | Built and staged with this module, never linked; loaded by name at run time. A monolithic build links them in |
| `PublicIncludePathModuleNames`, `PrivateIncludePathModuleNames` | Headers only, no link |
| `PublicIncludePaths`, `PrivateIncludePaths`, `InternalIncludePaths`, `PublicSystemIncludePaths` | Extra include folders, relative to the module folder or absolute |
| `PublicDefinitions`, `PrivateDefinitions` | Preprocessor definitions |
| `PublicAdditionalLibraries`, `PublicSystemLibraries` | Libraries every consumer links; system libraries by name (`ole32`, `dl`) |
| `RuntimeDependencies` | Files staged next to every executable that loads the module, each with a ship condition |
| `CompilerFlags`, `LinkerFlags` | Raw flags |
| `SourceDirectories`, `ExcludeSourcePatterns` | Compile other folders than `Private/`, or drop sources by name |
| `bUseUnity`, `UnityChunkSize`, `UnityExclude` | Unity (jumbo) builds |
| `PrivatePCHHeaderFile` | A precompiled header |
| `OptimizeCode` | `Default`, `Never` (always debuggable) or `Always` (optimized even in `debug`) |
| `bUseHeaderTool`, `HeaderToolDirectories` | Run the reflection code generator over these folders (`Public/` when empty) |
| `ShaderDirectories`, `ShaderArchive`, `AddShaderSourceDirectoryMapping` | Shaders this module compiles; see [Shaders and cook](/docs/build-tool/shaders-and-cook/) |
| `EmbeddedContentDirectory` | A folder (`Content` by default) linked into the binary as read-only data |
| `IconPath`, `bIsWindowsApp`, `bIsMacOSBundle` | Executable icon and windowed or bundle form |
| `bExplicitBuildOnly` | Built only when named with `-t` or needed by something that is |
| `BinaryType` | Overrides the binary kind the conventions pick |
| `Category` | Set only where the folder cannot say it; see below |

The rules can read the target through `Target`: `Target.Platform`, `Target.Configuration`, `Target.Type`, `Target.bIsMonolithic`, `Target.bWithOnline`, `Target.bIsServer`, the SDK switches and `Target.GetOption<T>(key, default)` for a custom `-o` option. Helpers name the engine's folders: `EngineDirectory`, `EngineModuleDirectory(name)`, `ThirdPartyLibDirectory(lib)`, `ThirdPartyLinkFile(lib, file)`, `BrandingFile(path)`, `ProjectDirectory`.

## Module types

| `Type` | What it is |
|---|---|
| `ModuleType.CPlusPlus` (default) | Compiled from the module's sources. A target's launch module is an executable, a module with no sources is header-only, anything else a shared library (a static one in a monolithic build). |
| `ModuleType.External` | A prebuilt library: include paths, libraries and runtime files only. |

Third-party libraries are external modules under `Engine/Source/ThirdParty/<Lib>/`, with their static and import libraries in `Lib/<platform>/` and their runtime files in `Engine/Binaries/ThirdParty/<Lib>/<platform>/`, where `<platform>` is a platform id such as `win-x64`:

```csharp title="Engine/Source/ThirdParty/zstd/zstd.Build.cs (excerpt)"
public class zstd : ModuleRules
{
	public zstd(ReadOnlyTargetRules Target) : base(Target)
	{
		Type = ModuleType.External;
		PublicIncludePaths.Add("Include/zstd");

		if (Target.Platform == TargetPlatform.Win64)
		{
			PublicAdditionalLibraries.Add("Lib/win-x64/zstd_static.lib");
		}
		else if (Target.Platform == TargetPlatform.Linux)
		{
			PublicAdditionalLibraries.Add("Lib/linux-x64/libzstd_static.a");
		}
	}
}
```

A runtime file added with a ship condition decides whether a game package carries it: `Always`, `SteamEnabled`, `DiscordEnabled`, `Upscalers`, `EditorOnly`, or `AutoSubtitles` (ONNX Runtime and its WebGPU provider, shipped only when the project turns on auto-subtitles) <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Modules/ShipCondition.cs" />. `mbt thirdparty` rebuilds the vendored libraries from source.

## Module categories

The group folder a module sits in is its category, as in Unreal <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Modules/ModuleCategory.cs" />:

| Folder | Category | May link into |
|---|---|---|
| `Engine/Source/Runtime`, `Engine/Source/ThirdParty` | Runtime | Anything |
| `Engine/Source/Editor` | Editor | Editor, Program and Test targets; never a Game or Server target, never the `release` or `profile` configuration |
| `Engine/Source/Developer` | Developer | Any target, never the `release` or `profile` configuration |
| `Engine/Source/Programs` | Program | Program targets only |
| A project, a template, anything outside the engine | Game | Anything |

Only the dedicated server's host declares a category in its rules (`Server`), because it is Runtime code the folder cannot tell apart. A `-t` build whose launch module links a module its target type or configuration rules out fails with the reason, for example `Editor modules never link into a Game target`. Under `release` and `profile`, a full build simply leaves those modules out. A module named like a configuration is a rules error.

## Targets

```csharp title="Engine/Source/MowoServer.Target.cs"
public class MowoServerTarget : TargetRules
{
	public MowoServerTarget(TargetInfo Target) : base(Target)
	{
		Type = TargetType.Server;
		LaunchModuleName = "MowoServer";
		bSeparateOutputTree = true;
		GlobalDefinitions.Add("WITH_SERVER=1");
	}
}
```

A target file is named `<Target>.Target.cs` and declares `<Target>Target : TargetRules` with a `TargetInfo` constructor <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/TargetRules.cs" />. Its fields:

| Field | Meaning |
|---|---|
| `Type` | `Game`, `Editor`, `Server`, `Program` or `Test` |
| `LaunchModuleName` | The module whose binary is the executable |
| `OutputName` | The executable's name; empty uses the launch module's |
| `ExtraModuleNames` | Further modules built with the target; an executable here builds beside the launch module |
| `GlobalDefinitions` | Definitions every module of the target compiles with |
| `LinkType` | `Default` (monolithic when the build asks for it or the platform is mobile), `Modular` or `Monolithic` |
| `Configurations`, `Platforms` | Where the target builds; empty is everywhere |
| `bSeparateOutputTree` | The target composes some module differently, so its binaries build into `Engine/Binaries/<platform>/<config>-<tree>/` (`dev-server`, `dev-noonline`) instead of the shared configuration folder |
| `bWithOnline` | `false` leaves the session, replication and transport layer out |
| `bBuildEnabledPlugins` | Build the enabled engine plugins with the target |
| `bEnableSteam`, `bEnableDiscord`, `bEnableMowoOnline`, `bEnableTracy`, `bEnableFSR`, `bEnableXeSS`, `bEnableStreamline`, `bEnableAntiLag2` | SDK switches |
| `bStaticThirdParty` | Link third-party static archives instead of their DLLs where both exist |
| `LogFloor` | The lowest log level compiled in |

The engine's targets sit at the top of `Engine/Source/`: `MowoEditor`, `MowoGame`, `MowoGameNoOnline`, `MowoServer`, `MowoProjectLauncher` and the Test targets. Programs keep theirs beside their sources in `Engine/Source/Programs/<Name>/`. Run `mbt info` to list them.

### A project's targets

A project created from a template carries a game target and an editor target in its `Source/` folder <Source path="Templates/TP_Coop/Source/TP_Coop.Target.cs" />:

```csharp title="Source/MyGame.Target.cs"
public class MyGameTarget : TargetRules
{
	public MyGameTarget(TargetInfo Target) : base(Target)
	{
		Type = TargetType.Game;
		LaunchModuleName = "MowoGame";
		OutputName = "MyGame";
		ExtraModuleNames.Add("MyGame");
	}
}
```

The game target launches the engine's player, `MowoGame`, under the project's name, with the game module built beside it. A project's module or target shadows a template's of the same name, so a project scaffolded from a template loads beside it.

## Build options

`-o KEY=VALUE` on `mbt build` passes an option to the rules. The ones the target reads <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/TargetRules.cs" />:

| Option | Default | Effect |
|---|---|---|
| `MOWO_MONOLITHIC` | `false` | Link the engine statically into the executable |
| `MOWO_ENABLE_STEAM`, `MOWO_ENABLE_DISCORD`, `MOWO_ENABLE_MOWO_ONLINE` | `true` | Build the platform plugins |
| `MOWO_ENABLE_TRACY` | per configuration | The Tracy profiler; on in `dev` and `profile` when unset |
| `MOWO_ENABLE_FSR`, `MOWO_ENABLE_XESS`, `MOWO_ENABLE_STREAMLINE`, `MOWO_ENABLE_ANTILAG2` | per RHI | Vendor SDKs; each RHI decides by whether the SDK is vendored when unset |
| `MOWO_WITH_AUTO_SUBTITLES` | `false` | Build the speech recognizer behind auto-subtitles |
| `MOWO_LOG_FLOOR` | empty | Compile out log lines below `info`, `warning` or `error` |

Any other key reaches a project's rules through `Target.GetOption<T>(key, default)`.

## Rules scopes and caching

`mbt` compiles every rules file of a scope into one assembly and caches it in `.mbt-cache/Rules/<Scope>.dll` with a manifest of every file's size and time <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/RulesAssembly.cs" />. The scopes are the engine (the Runtime, Editor, Developer and ThirdParty groups plus the targets at the top of `Engine/Source`), the programs, the engine plugins, each template and each project passed with `--extra-source`. `Internal/` headers are visible within a scope only.

## Migrating from `.mbt.cs`

Rules used to be `.mbt.cs` files with a `Configure(ModuleContext)` method. The build ignores them now and lists the ones it saw. `mbt migrate-rules` converts them <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/MigrateRulesCommand.cs" />:

```powershell
./mbt.cmd migrate-rules D:/Projects/MyGame/Source --check
./mbt.cmd migrate-rules D:/Projects/MyGame/Source
```

The `Configure` body becomes the constructor, context members become fields, dependency names lose their `MowoEngine.` prefix, and lines the folder conventions now cover are dropped. An executable module also gets a `.Target.cs`. What the converter cannot place is reported <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/RulesMigrator.cs" />. `--keep` leaves the old files beside the new ones; `--check` writes nothing and fails when anything would be converted.
