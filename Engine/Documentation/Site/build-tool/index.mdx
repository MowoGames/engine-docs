**MowoBuildTool**, run as `mbt`, is the engine's build system, modeled on Unreal Build Tool. It is a C# program on .NET 10 that lives in `Engine/Source/Programs/MowoBuildTool/`. It compiles the engine and your game, compiles shaders, cooks and packs content, generates IDE projects, scaffolds projects, classes and programs, runs the tests and packages builds. There is no CMake and no separate configure step.

## Rules are C# files

Every module has a `<Module>.Build.cs` next to its sources, and every binary a `<Target>.Target.cs`: small C# classes that say what the module needs and what the binary is. Because the build description is ordinary C#, platform checks and feature switches are plain `if` statements.

```csharp title="Source/MyGame/MyGame.Build.cs"
public class MyGame : ModuleRules
{
	public MyGame(ReadOnlyTargetRules Target) : base(Target)
	{
		PublicDependencyModuleNames.Add("EngineLoop");

		bUseHeaderTool = true;
		HeaderToolDirectories.Add("Public/MyGame");
	}
}
```

Folders replace most lines: `Public/` and `Classes/` are public include paths, `Private/` holds the sources, new `.cpp` files are picked up automatically. `mbt` compiles all rules files of a scope into one assembly with Roslyn and caches it in `.mbt-cache/Rules/`, so a build that changed no rules runs no compiler for them <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Rules/RulesAssembly.cs" />. [Modules and targets](/docs/build-tool/modules-and-targets/) covers the files.

## Running mbt

Run `mbt` through the wrapper at the engine root: `mbt.cmd` on Windows, `mbt.sh` on Linux and macOS. On the first run the wrapper publishes `mbt` as one self-contained executable into `Engine/Source/Programs/MowoBuildTool/publish/`, and it publishes again whenever a source file of `mbt` (or of the header tool it runs) is newer than that executable <Source path="mbt.cmd" />. The first run needs the .NET 10 SDK; later runs only start the published file.

```powershell
./mbt.cmd doctor
./mbt.cmd build
./mbt.cmd build -t MowoEditor -c Development
./mbt.cmd info
```

`mbt` finds the engine by walking up from the current directory, so you can run it from anywhere inside the checkout. If a publish fails, the wrapper refuses to run the previous `mbt` against newer sources and exits 1.

### Global options

Every command takes these <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/RootCommandFactory.cs" />:

| Option | Meaning |
|---|---|
| `-v, --verbose` | Verbose output |
| `--dry-run` | Show what would be done without doing it |
| `--progress console\|json` | `json` writes one JSON object per line (`progress`, `diagnostic`, `stage`, `complete`) for tools that drive `mbt`, such as the editor <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Utils/ProgressReporter.cs" /> |

## What a build does

<Flow steps={["Compile rules", "Resolve modules", "Header tool", "Compile", "Link", "Pack archives"]} highlight={3} caption="One mbt build. Shaders compile beside the C++ build, from its start." />

1. **Compile rules.** Every `.Build.cs` and `.Target.cs` in scope, or the cached assembly.
2. **Resolve modules.** `-t <name>` names a target first and a module second. A target builds its launch module, its `ExtraModuleNames` and, for game, editor and server targets, the enabled plugins. Without `-t`, `mbt build` builds every module. A module that links one its target type or configuration rules out fails the build: an editor module in a game, a developer module in Shipping.
3. **Header tool.** For every module with `bUseHeaderTool`, the reflection code generator runs in process and writes the generated code the module compiles with.
4. **Compile.** Each translation unit is fingerprinted from its source, its flags and the headers it included last time, and only changed units recompile <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Graph/BuildCache.cs" />. The fingerprints live in `.mbt-cache/`.
5. **Link** each module into a shared library (or a static one in a monolithic build) and each target into an executable.
6. **Pack archives.** Modules that declare a shader or content archive get it compiled and packed beside the binaries.

Only one build runs per checkout at a time: a second `mbt` waits for the first, because concurrent builds share `.mbt-cache` and would corrupt each other's objects <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Utils/BuildLock.cs" />.

`--shared-cache <folder or https bucket>` (or `MBT_SHARED_CACHE`) shares compiled objects across a team: a changed translation unit is pulled from the cache when another machine already compiled it with the same source, headers and flags, and published there otherwise. `--shared-cache-read-only` pulls without publishing.

## Where output goes

Binaries land in `Engine/Binaries/<Platform>/`, with the configuration in the file name: `MowoEditor.exe` in Development, `MowoEditor-Win64-Debug.exe` in Debug. Objects and generated code go to `Engine/Intermediate/Build/`. Every binary finds the engine from its own location, so the working directory does not matter. [Output layout](/docs/build-tool/output-layout/) has the details.
