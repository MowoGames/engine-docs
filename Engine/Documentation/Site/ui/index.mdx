Mowo has one UI framework. **Arc** draws every panel of Mowo Editor and every menu and HUD in a shipped game. **ArcUI** is the game-UI layer built on top of Arc. If you know Unreal, Arc plays the role of Slate and ArcUI plays the role of UMG.

This section covers both halves: how Arc lays out, styles and routes input to widgets, how ArcUI turns a `.ui` asset into a live screen, the designer you author those assets in, the player settings screens that ship with the engine, and how game text is localized.

## Two layers, one widget set

<Flow steps={["arc-style.json tokens", "Arc widgets (C++)", "ArcUI factory", ".ui screen", "Screen stack overlay"]} highlight={3} caption="Arc supplies widgets and style; ArcUI builds screens from assets and mounts them over the game view." />

| Layer | Module | What you use it for |
| --- | --- | --- |
| **Arc** | `MowoEngine.Arc` (namespace `Arcf`) | C++ widgets, layout, focus, input routing, text, docking, the style set. The editor is written directly against it. |
| **ArcUI** | `MowoEngine.ArcUI` | Game screens as assets: the `.ui` format, `.theme` themes, the widget factory, data bindings, animations, the screen stack, world-space widgets and the settings, rebind and lobby screens. |

Arc's public dependencies are SDL3 and MDF; its font and render back ends are private. ArcUI sits above Arc and the ECS component tier and depends on the Visual Scripting module, so a screen can call graphs.

<Callout type="engine">

Because the editor and the game share one widget set, a widget in a game HUD is the same class the editor uses in its panels. `FArcWidgetFactory` builds `.ui` nodes into real `Arcf` widgets such as `ATextBlock`, `AButton` and `ASlider`, not into a separate game-only tree <Source symbol="FArcWidgetFactory" />.

</Callout>

## How a game screen gets on screen

<Steps>
<Step title="Author the screen">

Create a `.ui` asset with **More > Arc Widget** in the Content Browser and lay it out in the [ArcUI Designer](/docs/ui/arcui-designer/). The asset stores a widget tree, bindings, events, animations, and an optional theme and controller class.

</Step>
<Step title="Mount it">

Attach an `ArcUI` component (fields `asset`, `z_order`, `visible`, `auto_focus`) to an entity, or push the screen from code with `PushScreen(assetPath, zOrder, modal)` <Source symbol="ArcUIComponent" /> <Source symbol="CArcUIScreenStack::PushScreen" />. For a widget in the 3D world, such as a nameplate, use an `ArcUIWorldWidget` component instead <Source symbol="ArcUIWorldWidgetComponent" />.

</Step>
<Step title="Let the stack run it">

`CArcUIScreenStack` builds the tree, composites every screen into one overlay, re-resolves bindings every tick, routes widget events and drives gamepad focus <Source symbol="CArcUIScreenStack" />.

</Step>
</Steps>

Details are on [ArcUI screens](/docs/ui/arcui-screens/).

## Current limits

- A screen stack keeps one controller instance per class, keyed by class name, so two screens with the same controller class share its variables. `MUIStatics` talks to a single process-wide active stack.
