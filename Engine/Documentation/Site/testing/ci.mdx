Continuous integration is GitHub Actions, on GitHub's own runners. Today it runs **only the documentation jobs**: it keeps the generated reference data in step with the code, lints the guides and publishes them to the website. **CI builds no C++, runs no engine tests and no build-tool unit tests.** A green run means the documentation is consistent and nothing more <Source path=".github/workflows/docs.yml" />.

The real gate for engine changes is `mbt test` on a developer machine. See [Running tests](/docs/testing/running-tests/).

## When the workflow runs

The `docs` workflow starts for pull requests, for pushes to the `dev` branch and for release tags (`v<major>.<minor>…`). Jobs run in the `mcr.microsoft.com/dotnet/sdk:10.0` container, skip Git LFS downloads, and a newer push to the same branch cancels a superseded run.

## The jobs

| Job | Runs | Fails when |
|---|---|---|
| `docs-reference` | `./mbt.sh docs`, then compares `Engine/Documentation/Generated` with the commit | On a pull request: the generated data drifted from the code |
| `docs-lint` | `./mbt.sh docs --lint --require-verified` | A guide has a broken source, symbol, fact or link, or a page without `verifiedAt` |
| `docs-publish` | `./mbt.sh docs --bundle` into the `engine-docs` repository, then moves the website's `engine-docs` submodule to it | A push fails or a deploy key secret is not set. Runs on `dev` and on release tags |

### docs-reference

Regenerates the API, console, command-line and facts data from the code <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/DocsCommand.cs" />. What it does with a difference depends on the pipeline source:

- On a **pull request**, it is a read-only gate. If the generated data differs from what is committed, the job fails and asks you to run `./mbt.sh docs` locally and commit the result.
- On **`dev`**, it commits the regenerated data back to the branch with the job's own `GITHUB_TOKEN`. A push made with that token starts no workflow, so the bot commit does not trigger another run.

### docs-lint

Checks every guide under `Engine/Documentation/Site/`: frontmatter, that each `sources` path exists, that each cited symbol resolves, that each fact id exists, and links. `--require-verified` makes a page without `verifiedAt` an error.

## How the docs reach mowoengine.com

The website does not read the engine repository. It pins `MowoGames/engine-docs` as its `engine-docs` submodule and builds from that. `docs-publish` fills that repository with `mbt docs --bundle` <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Docs/SiteDocsBundle.cs" />:

- `Engine/Documentation/Site/` and `Engine/Documentation/Generated/`, at their engine paths;
- `bundle.json`: the engine commit, branch and version, the date each guide and each generated file last changed, and the release snapshots;
- a `.gitattributes` that stores every file with LF line endings, written on each run because the bundle replaces the directory's contents;
- `versions/<tag>/`: `Site/` and `Generated/` as of the newest tag of each minor version.

The job then commits the new submodule commit to the website's `dev`, and that push deploys the site. It writes to the two repositories with deploy keys, one per repository, kept as the secrets `ENGINE_DOCS_DEPLOY_KEY` and `MOWOENGINE_COM_DEPLOY_KEY`; unlike `GITHUB_TOKEN`, a deploy-key push starts the website's deploy workflow. A release tag runs the same job, so a new tag publishes its snapshot without waiting for the next commit.

To build the bundle yourself:

```powershell
.\mbt.cmd docs --bundle ..\engine-docs
```

## What CI does not run

| Not in CI | Consequence |
|---|---|
| Any engine build | A change that does not compile still gets a green run |
| `mbt test` and every C++ case | No headless, GPU, editor, packaged or release case runs on the server |
| The build tool's C# unit tests | `MowoBuildTool.Tests` runs only through `mbt test` locally |
| Sanitizer runs | `--asan`, `--ubsan` and `--tsan` run only locally |
| Windows or macOS jobs | The engine's main platforms are never built by CI |

Build, test and packaging jobs existed in earlier versions of the pipeline (on GitLab) and were removed. The ROADMAP lists bringing back a build and CPU-test job, starting with Linux third-party binaries, as open work <Source path="Engine/Documentation/ROADMAP.md" />.

<Callout type="note">
When a `mbt test --cpu-only` run skips a quarter or more of the cases, it prints a coverage warning: those GPU cases run nowhere until you run `mbt test` on a machine with a GPU <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/TestCommand.cs" />.
</Callout>

## Before you merge

Because CI cannot see engine regressions, run the suite yourself.

<Steps>
<Step title="Run the full suite on your machine">

```powershell
.\mbt.cmd test
```

A full, unfiltered run also builds and launches the release player and boots the server tree. It exits 0 only when nothing failed and nothing was skipped.
</Step>
<Step title="Treat skips as missing coverage">
If your change touches a backend or feature your machine cannot run, the matching cases skip. `--allow-skips` makes the run exit 0, but those cases are still unverified. Say so in the pull request.
</Step>
<Step title="Regenerate the reference data if you changed public headers, console variables or mbt options">

```powershell
.\mbt.cmd docs
.\mbt.cmd docs --lint
```

Commit the result with your change, or `docs-reference` fails on the pull request.
</Step>
<Step title="Attach the JUnit report if it helps review">
`build/TestResults/junit.xml` records every case with its status and failure detail.
</Step>
</Steps>
