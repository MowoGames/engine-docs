`mbt test` is the gate for engine changes. It builds every target, runs every case of the six test executables in its own process, runs the C# unit tests, and writes a JUnit report. This page covers the command, its options, how to read the result, and how to run one case by hand.

## Run the suite

<Steps>
<Step title="Run everything">
From the engine root:

<CodeTabs>

```powershell tab="Windows"
.\mbt.cmd test
```

```bash tab="macOS"
./mbt.sh test
```

</CodeTabs>

The default configuration is `debug`: several cases (Live Coding, crash symbolisation) judge unoptimised code.
</Step>
<Step title="Let it build first">
Unless you pass `--no-build`, the command first runs `mbt build -c <config>` for every target. If that build fails, no case runs and the exit code is 1. The suite starts the test executables and the hosts they launch, so stale executables against fresh libraries would give false failures <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/TestCommand.cs" />.
</Step>
<Step title="Read the summary">
Each case prints `PASS`, `FAIL`, `SKIP` or `CRASH` with its duration. The run ends with the totals, the names of the failed cases and the path of the JUnit report.
</Step>
</Steps>

<Callout type="warning">
Do not edit sources while a full `mbt test` runs. The suite builds more than once (the release and server rows compile their own trees), so an edit mid-run lands in some binaries and not others.
</Callout>

## Options

The generated [mbt CLI reference](/docs/reference/mbt-cli/) lists every option. The ones you use most:

| Option | Effect |
|---|---|
| `-f`, `--filter <text>` | Only cases whose name, switch or description contains the text. The same text filters the C# tests |
| `-t`, `--tag <tag>` | Only cases carrying every given tag (`core`, `runtime`, `renderer`, `net`, `programs`, `editor`, `gpu`, `packaged`, `visual-script`, …). Repeatable |
| `--target <exe>` | Only these test executables, such as `CoreTests`. Repeatable |
| `--shard=<i>/<n>` | One shard of the planned cases: `--shard=2/4` takes every fourth case from the second |
| `--cpp` / `--csharp` | Only the engine cases / only the C# unit tests |
| `--cpu-only` | Skip every case that needs a GPU device. Each is recorded as a skip |
| `--allow-skips` | Exit 0 even when cases were skipped |
| `-c`, `--config <name>` | Configuration to test (`debug`, `dev`, `profile`, `release`, `debuggame`). Default `debug` |
| `--no-build` | Do not build first. Assumes the binaries are current |
| `--capture-baselines` | Let screenshot cases record a missing or drifted reference image |
| `--asan`, `--ubsan`, `--tsan` | Build and run the CPU cases under a sanitizer, in a separate tree. One at a time; `--tsan` needs Linux or macOS |
| `--perf-gate` | Fail the run when a performance-trend series regressed past its threshold. Without it a regression is reported but does not fail |
| `--monolithic-package` | Build the packaged-case package with the engine linked statically. This triggers a full static engine build |

Common loops:

```powershell
.\mbt.cmd test --cpp --tag visual-script              # every Visual Scripting case
.\mbt.cmd test --cpp --cpu-only              # the GPU-free set
.\mbt.cmd test --target CoreTests --no-build # one executable, no rebuild
.\mbt.cmd test --filter curve-eval --no-build # one case by name
.\mbt.cmd test --csharp                      # C# unit tests only
```

A run with a filter, a tag, a target or a shard is a **partial run**: it skips the release and server rows, which cost a full extra compile.

### Sanitizers

A sanitizer run implies `--cpu-only`: a sanitizer over a GPU driver reports the driver's own allocator and stalls device start-up. It builds into its own tree, so switching the sanitizer on and off never rebuilds your ordinary binaries. Packaged and template cases are skipped with a reason, since they would run binaries the sanitizer never saw <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/TestCommand.cs" />.

## What the runner does to every case

`mbt test` asks each executable for its cases with `<Exe> --mowo-list-cases`, expands the backend fan-outs, applies your filters, and runs each case as:

```text
<Exe> -tc="<case>" -r=junit -o=build/TestResults/cases/<Exe>.<case>.xml --repo-root=<checkout> --test-timeout=165 [--gpu-validation] [--rhi=<backend>]
```

- **Two deadlines.** The executable's own watchdog fires first (`--test-timeout`, 165 seconds by default from the runner) and exits with code 4, naming the wedged case. The runner kills the process tree at 180 seconds as a backstop. A case can ask for a longer deadline <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool/Commands/TestCommand.cs" />.
- **No user config.** The kit adds `--no-user-config` to every case <Source path="Engine/Source/Developer/MowoTestKit/Private/TestCase.cpp" />.
- **GPU validation.** Cases that need a device get `--gpu-validation`, so a check that validation errors stay at zero means something.
- **Backends.** A case that names backends also runs as `<case>-<backend>` with `--rhi=<backend>`, on each backend the host links: D3D12 and D3D11 on Windows, Metal on macOS, Vulkan everywhere except macOS <Source path="Engine/Source/Programs/MowoBuildTool/src/MowoBuildTool.Core/Utils/SelfTestBackendAxis.cs" />. A Windows run never exercises Metal, and a Mac run never exercises D3D12.
- **No crash wizard.** Every case runs with `MOWO_NO_CRASH_REPORTER=1`, so a crash does not open the interactive crash reporter.

### Screenshot references

Some cases compare a downscaled capture against a reference image per backend, `Engine/Source/Developer/MowoTestKit/Fixtures/Screenshots/<name>.<Backend>.png`. A difference fails the case and writes `<name>.<Backend>.actual.png` beside the reference. A backend with no reference skips, naming the file. Pass `--capture-baselines` to record a missing reference, or to replace one the run drifted from; the case still reports a skip until you review and commit the new image <Source path="Engine/Source/Developer/MowoTestKit/Shared/ScreenshotBaseline.cpp" />:

```powershell
.\mbt.cmd test --cpp --no-build --allow-skips --capture-baselines --filter bloom-sky
```

Open every captured image before you commit it: it is the look every later run is held to.

## Results

### Case states

| Console | Cause | JUnit |
|---|---|---|
| `PASS` | Exit 0 | passed `testcase` |
| `PASS` with `[selftest-skip] …` lines | Passed, but a block of checks inside it did not run | passed `testcase` |
| `SKIP` with a reason | Exit 77. The reason comes from the `TEST SKIPPED:` line | `<skipped message="…"/>` |
| `FAIL` | Any other non-zero exit, or a timeout | `<failure>` |
| `CRASH` | A crash exit code, such as an access violation or a POSIX signal | `<failure>`, detail starts with `CRASH` |

### The JUnit report

Every run writes `build/TestResults/junit.xml`, with one suite per test executable plus `judged-from-outside` for the release and server rows and `perf-trends` for the trend verdicts. Each case's own doctest report stays under `build/TestResults/cases/`. A failed case's detail lists its failing lines and the tail of its output.

### Exit codes of mbt test

| Code | Meaning |
|---|---|
| 0 | Nothing failed, and nothing was skipped (or `--allow-skips` was given) |
| 1 | The pre-test build failed, or at least one case failed |
| 2 | Cases were skipped without `--allow-skips`, two sanitizers were requested, or no engine checkout was found |

When a quarter or more of the cases did not run, the summary also prints a coverage warning.

## Run one case by hand

The fastest loop is the test executable itself. The executables are ordinary doctest runners in the configuration's binaries folder, `Engine/Binaries/<platform>/<config>/`, and carry only their name (`Engine/Binaries/win-x64/debug/CoreTests.exe`, no extension on Linux and macOS) <Source path="Engine/Source/CoreTests.Target.cs" />:

```powershell
cd Engine\Binaries\win-x64\debug
.\CoreTests.exe --list-test-cases          # doctest's own listing
.\CoreTests.exe -tc=curve-eval-test        # one case
.\CoreTests.exe --curve-eval-test          # the same case, by its switch
.\RendererTests.exe -ts="*[gi]*"           # every case tagged [gi]
```

A case applies its own switches before its body runs, so `<Exe> -tc=<case>` alone reproduces what `mbt test` ran. Running a whole executable in one process is a convenience only: some cases leave global state behind, which is why the gate runs each in its own process.

Exit codes of a test executable:

| Code | Meaning |
|---|---|
| 0 | Passed |
| 1 | A case failed |
| 2 | No case matched the filter |
| 4 | The watchdog fired (`--test-timeout=<seconds>`, default 900, `0` turns it off) <Source path="Engine/Source/Developer/MowoTestKit/Private/TestMain.cpp" /> |
| 77 | Cases skipped and none failed |

When you run a GPU case by hand to compare with `mbt test`, add `--gpu-validation` so the conditions match.

## Running from the editor

The editor's **Automation** panel lists the same cases and runs them with the arguments `mbt test` would use. It never builds and cannot run packaged cases. See the [Testing overview](/docs/testing/).
